# Behaviour reference

How the plugin behaves beyond the happy path. The [README](../README.md) has the short version.

## The OpenCode version

Each release of the plugin is built and tested against one OpenCode V2 version, the exact
`@opencode/plugin` version pinned in its `package.json`; the README's [Supported OpenCode
version](../README.md#supported-opencode-version) shows the newest three rows. The end-to-end suite
runs on that version with every change, and once more on the newest `@opencode/cli` release on every
push to `main` and nightly, where a failure is a warning. Every release and its version:

<!-- compat-table:end -->

Nothing in OpenCode checks the version: `opencode plugin add` installs the plugin on any V2 host,
and the loader warns about nothing. The plugin loads on hosts from 2.0.4 on and fails to load on
2.0.0 to 2.0.3, which lack a domain the plugin API gained in 2.0.4. On a newer host, tools may still
break. The terminal part relies on the host to provide its UI modules and is tested on OpenCode
2.0.32 only; the server part works on older V2 hosts from 2.0.4 on.

When the running OpenCode reports a version other than the pinned one (an older server, a
development build and one whose plugin context reports no version included), the plugin writes one
line to the server log (`opencode serve --print-logs` shows it) when it loads, once per project
location, then loads and registers its tools as usual; no tool result mentions it:

```
opencode-courier 0.2.0 was built and tested against OpenCode 2.0.22; this server is 2.0.30 (channel beta). Its tools may fail: see every release and the OpenCode it is pinned to, https://github.com/ivopogace/opencode-courier/blob/main/docs/reference.md#the-opencode-version
```

Check yours with `opencode --version`.

## Updating the plugin

Install the plugin by name, without a version. OpenCode only checks plugins for updates when their
entry is not an exact version: `opencode-courier`, `opencode-courier@latest` or
`opencode-courier@^0.2.0` is checked against npm, but `opencode-courier@0.2.1` counts as fixed, and
`opencode plugin check`, `opencode plugin update` and *check for updates* (ctrl+r) in the TUI's
`/plugins` dialog never offer it a newer release. If your entry carries an exact version, replace it
with the name and restart OpenCode:

```bash
opencode plugin remove opencode-courier@0.2.1   # the entry exactly as it appears in plugins
opencode plugin add opencode-courier
```

Then `opencode plugin check` lists `courier` with `(update available)` when a newer release exists,
and `opencode plugin update` installs it. If an unpinned entry still shows no update after a release,
the check itself may have failed: OpenCode treats a failed check as "no update" and only writes
`failed to check plugin update` to its log (`~/.local/share/opencode/log/`); the check uses your npm
configuration, so look at the registry and proxy settings in your `.npmrc`. After an update OpenCode
loads the new copy next to the old one until the old one unloads; while both run, each scheduled
message, released group, notice and question still goes out once.

## The tools

Each tool's parameters, `?` marking an optional one; the sections below say how each behaves.

| Tool | Parameters | Does |
|---|---|---|
| `courier_spawn` | `task`, `title?`, `agent?`, `isolate?`, `group?` | Creates a session on the parent's [model](#the-childs-model), in its own git worktree with `isolate: true` ([nested isolation](#nested-isolation)), sends it the task plus a brief, and returns at once. With a `group`, its report is held with the [join group](#join-groups)'s. Refused past the [limits](#session-trees-and-their-limits). |
| `courier_send` | `sessionID`, `message`, `status?`, `artifacts?`, `queue?` | Delivers a message to a session, signed with the sender's id, waking it if idle: steered into its running turn, or, with `queue: true`, after the turn ends. From a child to its parent, a `status` makes it the child's [report](#a-childs-report), with its `artifacts` (`branch`, `commits`, `files`, `checks`); from a member of a join group, a `done`, `partial` or `failed` report is held with the group. |
| `courier_status` | `sessionID` | One look at a session: the outcome of its last turn, how long it has been idle, its last reply and the permission requests and questions it waits on (`pending`). For check-ins, not for waiting. |
| `courier_children` | `sessionID?` | Lists the sessions this one (or `sessionID`) started with `courier_spawn`, each with what `courier_status` reports plus its directory, whether it is isolated, when it was started and, for one started in a group, the group and its [report's standing](#join-groups). |
| `courier_tree` | `sessionID?` | Lists the [whole tree](#seeing-and-stopping-a-subtree) under this session (or `sessionID`), depth first, each with what `courier_children` shows plus its depth, its parent and its report state. At most `maxTotal` sessions: the live ones first, then the newest. |
| `courier_stop` | `sessionID`, `cleanup?` | [Stops](#seeing-and-stopping-a-subtree) a session started from this one, directly or through others, and every session under it, deepest first, and cancels the `courier_later` messages scheduled for them; `cleanup: true` also removes their worktrees by `courier_cleanup`'s rules. |
| `courier_cleanup` | `sessionID`, `force?` | Removes an isolated child's worktree and forgets the child; a worktree with uncommitted changes or commits on no branch, tag or remote is kept unless `force: true` ([worktree cleanup](#worktree-cleanup)). A join group member that has not reported is [dropped from its group](#join-groups). |
| `courier_answer` | `sessionID`, `requestID`, `reply?`, `message?`, `answers?` | Answers a [permission request](#a-child-that-asks-for-permission) (`reply`: `once`, which OpenCode first asks the person about in this session, or `reject`, with an optional `message`) or passes the person's answer to a [question](#a-child-that-asks-a-question) (`answers`) that a session started from this one waits on. |
| `courier_later` | `message`, `sessionID?`, `delayMinutes?` or `at?` | Schedules a message for a session (this one by default) in `delayMinutes` (a number, or a string of one) or `at` an ISO 8601 time, and returns its id. When due it is delivered like `courier_send`, queued behind any running turn and waking the session if idle ([scheduled messages](#scheduled-messages)). |
| `courier_cancel` | `id` | Drops a message scheduled with `courier_later`. |
| `courier_subscribe` | `topic`, `sessionID?` | Subscribes a session (this one by default) to [webhook](#webhooks) deliveries for a topic: `owner/repo`, `owner/repo#12` (one pull request or issue) or a name for `/hook/<name>`. Each matching delivery arrives as a message, queued behind any running turn and waking the session if idle. |
| `courier_unsubscribe` | `sessionID?`, `topic?` | Drops one topic, or all of a session's when `topic` is omitted. |
| `courier_recall` | `sessionID?` | One look at the [records](#memory) of the session trees of this project: one line per tree, the pinned first and then newest first, its lesson after the facts, or with `sessionID` the record of the tree under that top session in full. Notes the call on the caller's own tree's record, and counts the look on the others'. Hidden from a leaf. |
| `courier_note` | `text` | Writes `text`, one line of at most 300 characters, as the [lesson](#the-lesson) of the caller's own session tree; a sub-orchestrator's is marked with its depth, a second call replaces the first. Refused with a longer text, from a leaf, from a tree with no record, with an empty text and with the memory option off. Hidden from a leaf. |

## The child's model

A child runs on the model its parent is using, not on OpenCode's default. The exception is a child
given an `agent` that names a model of its own: that agent's model is kept. If the parent's model
cannot be looked up, the child is started anyway, on OpenCode's default.

## Native child sessions

Off by default. With `"nativeChildren": true` in the plugin's `options`, `courier_spawn` creates a
child started without `isolate` with OpenCode's own `parentID`, the calling session, instead of a
location; the child takes its parent's location. Like the limits, the option is read by the instance
of the location the calling session runs in, so set it once, in the global config; a value other than
`true` or `false` is not used, and the server log says so when the plugin loads.

```jsonc
{
  "plugins": [{ "package": "opencode-courier", "options": { "nativeChildren": true } }]
}
```

The child still carries `metadata.courier.parentID`, and the courier's own lineage (the limits, the
roles, the relays, `courier_children`, `courier_tree`, the status entry) still reads the
[roster](#roster), which notes the child as native. An isolated child is created as before: OpenCode
takes a location or a `parentID`, never both. A child started without `isolate` by an isolated child
is a native child of that one, so a tree with isolated children shows in OpenCode's UIs as several
trees, split at each isolated child; `courier_tree` shows the whole.

OpenCode's own UIs treat a session's native children as its family, as they do the sessions of its
`subagent` tool: the TUI's view of a session that has no `parentID` lists the permission requests and
forms of every session under it and answers them there, its subagent tab lists the children, its
footer counts the running ones, and the session's cost includes theirs; the request dock of the paired
web, desktop or mobile app does the same for the open session and every session under it (read in
OpenCode's source; not tried on a device). What changes with it:

1. **Deleting a session deletes its native children**, and theirs; their isolated children are left.
   The plugin forgets each deleted child as it does any [deleted child](#worktree-cleanup).
   `courier_cleanup` and `courier_stop` never delete a session.
2. **What providers see.** A native child's model requests carry its parent's id as the cache-routing
   id (`x-session-affinity`, `X-Session-Id`, `x-opencode-session` and the `promptCacheKey`), plus two
   headers naming the parent (`x-opencode-parent-session-id`, `x-parent-session-id`). OpenCode's
   GitHub Copilot provider sends `X-Interaction-Type: conversation-subagent` and `x-initiator: agent`
   for such a session, which Copilot meters differently; the plugin was not tried on Copilot.
3. **Permissions.** OpenCode gives a session created with a `parentID` and no ruleset its parent's
   session-level ruleset. The courier passes an empty ruleset, so a child runs on its agent's rules
   alone, as without the option. A rule saved with `always` is the project's either way.
4. **Where asks are answered.** A native child leaves the TUI's session lists: it is reached from its
   parent's subagent tab or by id. Its own view lists none of its permission requests or forms; the
   view of the top of its native tree does: the session at the top of the courier's tree, or the
   isolated session nearest above it. The notice of a [form](#a-child-that-shows-a-form) names it.
5. **Who else answers.** The TUI's `autoaccept` permission mode, in the open top session's view,
   approves native children's requests once, and `opencode run`, while it runs a turn of the top
   session, takes them for its own subagents': approving with `--auto`, rejecting without, and
   cancelling their questions and forms.

**Questions: asked once, in OpenCode's own form.** While a native child's question call waits,
OpenCode shows its form in the view of the top of its native tree; when that is the top session, the
plugin tells its model with a notice marked `shown="native"`, which lists the questions, says that the
person answers them in OpenCode's own form, and that it is not to ask them itself; the top session's
question tool is not linked to that question, so even a model that asks anyway passes nothing on. The
child carries on in the same turn, and the top session is told once it is settled
(`answered="elsewhere"`). `courier_answer` still answers it, which withdraws the child's form. Once
the child's call is cut off (its turn stopped, a restart), its form is gone, and the question is
relayed as without the option. A question of a native child under an isolated session shows in that
session's view, not the top's, so it is relayed and linked as without the option, as is every question
of an isolated child.

**Permission requests: asked once, in OpenCode's own prompt.** A native child's permission request
whose native root is the top session is shown there as OpenCode's own permission prompt, bound to that
request, and on the paired app's dock; the plugin tells the top session's model with a notice marked
`shown="native"`, which tells it not to ask the person nor to call `courier_answer`, and to tell them
in one line at most and end its turn; it names the request's ids only for a person who tells the
model to answer for them. Once the person answers in OpenCode's prompt, the model is told it is
settled (`answered="<reply>"`). A `courier_answer` the model calls all the same prompts the person
[again](#a-child-that-asks-for-permission), in the top session, and the first answer counts. A native
child under an isolated session, an isolated child, and every child with the option off get the
notice as without the option.

Turn the option on only where the person sees OpenCode's own prompts and forms: the TUI, or the
paired app. A bare API client leaves a native child's questions and permission requests without a
prompt; `courier_answer` is the fallback, and `courier_status` lists them under `pending`.

## Session trees and their limits

Any spawned session can call `courier_spawn` too, so sessions form a tree: the session nobody
spawned is its top, at depth 0, the sessions it starts are at depth 1, and so on. Three options bound
the tree, each a positive integer, in the plugin's `options`:

| Option | Default | |
|---|---|---|
| `maxDepth` | `3` | The deepest a spawned session may be. A session at this depth cannot start sessions. |
| `maxChildren` | `5` | How many of the sessions one session started may be live at once. |
| `maxTotal` | `20` | How many spawned sessions may be live at once in one tree, anywhere in it; the top session is not counted. |

```jsonc
{
  "plugins": [{ "package": "opencode-courier", "options": { "maxDepth": 2, "maxChildren": 3 } }]
}
```

A spawn is checked by the instance of the location the calling session runs in, so set the options
once, in the global config. A value that is not a positive integer keeps the default, and the server
log says so when the plugin loads. A changed limit applies once OpenCode loads the plugin again.

**`courier_spawn` enforces them.** It works out the calling session's depth and tree from the
[roster](#roster) and refuses, with an error naming the limit and what to do instead (do the work
yourself, or end the turn and try again once a child has reported), when the child would be deeper
than `maxDepth`, or when `maxChildren` or `maxTotal` sessions are already live. A session is live
while its turn runs, while it [owes its parent a report](#a-child-that-ends-without-a-report), or
while a session below it is live; so a child that ends its turn without reporting keeps counting
until it does, and a session that has split its task and ended its turn to wait for its children
counts too. One OpenCode no longer knows does not count. A session spawned by a release that kept no
report state, or whose state cannot be read, counts while its turn runs.

The checks run one at a time in the process, and a spawn under way counts until its child is on the
roster, so several `courier_spawn` calls made at once cannot get past a limit together, whichever
locations or copies of the plugin make them; two servers on one data directory do not see each
other's spawns under way. A failed roster read refuses the spawn; a failed look-up of a session
counts it as not running. A session whose roster entry could not be written, or was dropped after 14
days, starts its children as if it were the top of a tree.

**The brief says when to split.** A spawned session is told its depth and the limits. Below
`maxDepth` it is given a rule: split the task when it has 2 or more independent, substantial parts
touching separate files or areas, one session per part; do it itself when it is small, sequential or
tightly coupled; never start exactly one session for the whole task; and say which in one line of its
reply, `split: no, because …; considered: <the parts you weighed>` or `split: <n> parts: …`. A
session that splits ends its turn while its children work, checks and integrates each part itself,
and sends its parent one combined report. At `maxDepth` it is told to do the task itself. Every
spawned session is told how to [report](#a-childs-report). The text is `tree/text.ts`'s brief.

**A `context` hook names the role on every model request.** For a spawned session the plugin adds
one system part, `opencode-courier role: …`, naming its role and depth: `sub-orchestrator` below
`maxDepth`, with the limits, and `leaf` at it, which is told it cannot start sessions and whose
request goes without `courier_spawn`, [`courier_recall` and `courier_note`](#memory) in its tool
list. The hook is guidance and `courier_spawn` the guarantee: another plugin's hook can put the tool
back, and the call is still refused. A session nobody spawned that has started none gets a pointer
instead, `opencode-courier role: root, no sessions started yet`: before a task that touches several
files or areas, load the `courier-orchestrate` skill, call [`courier_recall`](#memory) once, and
decide whether to split it, saying which in one line of the reply; a request without `courier_spawn`
in its tool list gets no pointer. After its first spawn the session gets a `root orchestrator` part
with the limits instead. Every part begins with the same `opencode-courier role:` prefix, and the hook
adds none when one is there already, so a second copy of the plugin does not add its own; each part
is the same on every request of its session, so the provider's prompt cache holds. A child spawned by
a release before the roster's reverse index is taken, until the plugin next loads, for a session
nobody spawned; `courier_spawn` still enforces the limits.

## The courier-orchestrate skill

The plugin registers one OpenCode skill, `courier-orchestrate`, in every location it loads in, with
a description saying when to load it: at the start of any implementation task that may have
independent parts, or when a session was started by one. A model loads it with OpenCode's `skill`
tool, which asks the `skill` permission for it like any skill (a spawned session's request is relayed
to its parent as any other); a person activates it from the TUI's `/skills` dialog. How OpenCode
lists, loads and injects a skill: [plugin-api-notes.md](maintainers/plugin-api-notes.md#skills).

Its text is in `src/skill.ts`, snapshotted by `test/notices.test.ts`. It names no limits (the role
part and the brief give the session's own) and says, in order: call [`courier_recall`](#memory)
once, before deciding; decide whether to split or do, by [the brief's rule](#session-trees-and-their-limits),
keeping the deciding, checking and integrating while handing off the long reading and writing, and
weighing the parts an implementation task with one tightly coupled core still has (finding out what
the change needs, its e2e scenario, its documentation, a review by a session with fresh context), in
stages when the rest depend on names the core fixes; say which in one line of the reply; plan the
parts so that no two edit the same files; start them with one `courier_spawn` per part, all in one
[join group](#join-groups), `isolate: true` where parts edit files in parallel, and end the turn
without polling; read each [report](#a-childs-report) by its status; verify first-hand, running
checks through the project's scripts (`bun run <script>`, `npm run <script>`) so that one permission
rule covers them, since the orchestrating session's own permission prompts are relayed nowhere;
integrate by merging each reported branch, then `courier_cleanup`; report upward with one status for
the whole, or, at the top, one `courier_note` with the tree's [lesson](#the-lesson) when there is one
(step 8); and what to do when a part goes wrong: a [failed turn](#a-child-that-fails) or a [silent
end](#a-child-that-ends-without-a-report), a `courier_spawn` refused by a limit (never retry in a
loop), losing track (one `courier_tree`), a subtree to abandon (`courier_stop`). The real-model
smoke test's [recursive scenario](maintainers/real-model.md#recursive-orchestration) tries it against
free models.

## A child's report

A child reports with `courier_send` to the session that started it, giving a `status`: `done`,
`partial` (some of the task is left; the report says what and why), `blocked` (it needs a decision
from its parent, and the report carries a concrete ask) or `failed`. `courier_send` carries the
status as an attribute of the envelope the parent reads, `<courier from="<child>" status="done">`,
and in the delivered message's metadata (`status`). A status that is none of the four is refused;
`null` counts as none. With the status, a report may list `artifacts`: `branch`, a string, `commits`
and `files`, lists of strings, and `checks`, a list of `{ command, result }`. They go in the message
body after the text, in one fixed layout:

```
<courier from="ses_child" status="done">
Fixed the total in checkout.

Artifacts:
- branch: fix/checkout
- commits: abc1234 Fix the total
- files: src/checkout.ts, test/checkout.test.ts
- checks:
  - bun test: 412 passed
  - bun run typecheck: clean
</courier>
```

A field that is empty or not of its type is left out, and a check without a command too; nothing is
listed when no artifact is given.

**A status settles the report; a message without one is progress.** A message with a status from a
child to its parent settles the child's report, `blocked` too. One without a status is noted as
progress and settles nothing, so a child that sends "halfway there" and then ends its turn without a
report is [told to its parent](#a-child-that-ends-without-a-report), and the notice says that its
last message had no status. The tool's result tells the child which it was. A message to any session
but the parent is neither. A child an earlier release briefed was never told about statuses, so its
messages without one count as its report. The plugin acts on no status beyond settling the report.

## Join groups

Each report wakes the parent separately. A join group has the parent woken once: `courier_spawn`
takes an optional `group`, a name scoped to the calling session, and the reports of the sessions
started with the same name are held until every one of them has reported and the parent's turn that
started them has ended, then delivered in one message. A name is 1 to 60 letters, digits, dots,
dashes or underscores; any other is refused before anything is started, and `null` counts as none.
`courier_spawn`'s result says the child's report is held with the group.

**What is held, and what is not.** A report with status `done`, `partial` or `failed` from a member
to its parent is held, with its status, text and artifacts; its result tells the child so, with how
many members have reported. A held report still settles the child's report: the child stops [owing
one](#a-child-that-ends-without-a-report), stops counting against the
[limits](#session-trees-and-their-limits) once its turn has ended, and gets no notice of a silent end.
Everything the parent needs now passes through at once: a `blocked` report (the member stays out, and
reports again once it has its answer), progress, a failed turn, a turn ended without a report, a
permission request, a question and a form. A member that reports twice has its later report held in
place of the earlier.

**The release.** Once every member has a held report, or has left, and the parent's turn that
started the last of them has ended (a turn ends when it succeeds, fails or is interrupted, not when a
shutdown stops it), the group is released: the parent gets one message, waking it if idle, wrapped in
`<courier from="<members>" group="<name>" reports="<n>">`, `from` listing the sessions whose reports
it carries, comma-separated. The body names the group and counts the reports by status, and the
members without one, then lists every report in the order the members joined, each as `[i/n]
<sessionID> "<title>": <status>` followed by its text and its artifacts in [the fixed
layout](#a-childs-report), and after them the members that left without a report. The metadata
carries `group`, `reports` and `from`. The held reports are then dropped, and the group with them:
the name is free again. A session started into a group that is still open joins it, and the release
waits for it too. A member's report after the release is delivered on its own, as a report of a child
in no group.

**A member that leaves.** A member leaves the group without a report when its turn
[fails](#a-child-that-fails) or is interrupted (by the person, or by OpenCode after an hour without
activity; not by a shutdown), when its task could not be handed over, when OpenCode deletes its
session, or when the parent drops it with `courier_cleanup`. The group is then released once its
other members have reported and the parent's turn has ended, the message naming who left and why. The
parent hears of each as of a child in no group: a failed turn at once, in a notice with a line naming
the group (the group's message does not overtake that notice, unless a scheduler tick falls in the
moment between the two), a task not handed over as `courier_spawn`'s error, an interruption or a deletion only in
the group's message, and a drop in `courier_cleanup`'s result and the group's message. A group whose
every member left is dropped unsent.

A member that reports after all before the release rejoins with its report, and one whose report
comes in while the group's message is going out keeps it, for the next delivery. A member that has
reported keeps its held report whatever happens to its turn after, unless its next word to the parent
is a `blocked` report: that passes through, and the stale held report is dropped. A held report
outlives the member's [roster](#roster) entry: a member whose entry expires after 14 days goes from its
group with no trace when it has not reported, and otherwise stays until the release. A member that
[ends its turn without a report](#a-child-that-ends-without-a-report) is still out: the silent-end
notice says the group's other reports are held until it reports, or until the parent drops it. A
report that cannot be held, the storage failing as `courier_send` runs, is delivered on its own, and
the member dropped from the group.

**Dropping a member.** A member that will not report holds every other member's report back: one
that ended its turn without a report, one whose failure or interruption the plugin missed (its watcher
was resubscribing, or the server was down), or one the parent has given up on. The parent drops it with `courier_cleanup { sessionID }`, which [forgets the child](#worktree-cleanup),
removing its worktree first if it is isolated (one whose worktree is kept for its work is not
dropped). A member still out is first marked as left, then its roster entry and report state go; with
the parent's turn ended, its held reports reach it at once, in one message that names the member under
"Without a report" (`you dropped it with courier_cleanup`), and `courier_cleanup`'s result says it was
dropped (`group` in its metadata). A member whose report is held, or that already left, keeps it and
is not named as dropped. A dropped member that reports after all is delivered on its own. If its
membership cannot be read, `courier_cleanup` fails before it forgets anything. A dropped child is off
the roster, so it no longer counts toward the limits, and the plugin no longer tells the parent of
its failures or silent ends.

**The parent waits** on a group as on any children: while a member still owes it a report it has not
been told about, and, once the group is complete, for the message about to be delivered. So a
sub-orchestrator that has split its task into a group and ended its turn is not reported to its own
parent as having ended without a report, until the group's message has reached it and it ends a turn
without reporting.

**`courier_children`** lists, for a child started in a group, `group: { name, report }`, with `report`
one of `held`, `out`, `failed`, `interrupted`, `deleted` (it left), `released` (the group has been
delivered, or the child joined an earlier one of that name) or `unknown` (its membership could not be
read). A child whose group could not be joined when it was started is
recorded in no group, and `courier_spawn`'s result says so.

**Delivery.** The scheduler that delivers `courier_later` messages delivers released groups too, at
each tick, and at once when the parent's turn ends with a group complete, or a report, a failure, an
interruption, a deletion or a drop completes a group whose parent's turn has ended (with [two
servers](#two-servers-on-one-data-directory), up to a tick longer). Each release is delivered once,
and dropped only after the message has been delivered: a delivery that fails is tried again at the
next tick, while a crash between the delivery and the drop delivers it again after a restart. Held
reports live in the plugin's storage, so a restart loses none. A group whose parent OpenCode no
longer knows is dropped unsent. The group's message is steered into the parent's running turn or
starts one, whatever `queue` the members' `courier_send` calls gave; it makes a spawned parent owe a
report.

## A child that fails

For every failed turn of a spawned session (the model not available, the credentials missing, the
provider down) the plugin sends the parent a message from that child, marked `failed="<error type>"`,
with the child's title and the error, waking the parent if it is idle. The parent then decides:
message the child to have it try again, start a replacement, or carry on without it.

Every failed turn of a child is reported, also one that fails after the child has reported. A turn
that was interrupted is not a failure and is not reported, and neither is a failure that happens while
the OpenCode server is down or the plugin is not loaded; a `courier_later` check-in covers those.

## A child that ends without a report

A child's turn can end without failing and without a `courier_send` to its parent. So the plugin
keeps, for each spawned session, whether it owes its parent a report: from the moment its task or a
message delivered through OpenCode's inbox reaches it (a message from any session, a scheduled
message, a webhook delivery, or one of the plugin's notices) until it calls `courier_send` with its
parent's id and a [status](#a-childs-report), or its turn fails or is interrupted. What the person
types in the child's own session, and a compaction or move of it, does not make it owe a report: the
plugin tells these apart by the type OpenCode gives each item as it enters the inbox (`user`,
`synthetic`, `compaction` or `move`), remembered for the last 1000 items of spawned sessions; a
delivery whose item it did not see enter, such as one queued before a restart, counts as a message.
The task is noted by `courier_spawn` itself, just before it hands it over, and settled as failed if
handing it over fails.

When a turn of a spawned session ends without failing while it owes a report, the plugin sends its
parent a message from that child, marked `ended="without-report"`, with the child's title and its last
reply as `courier_status` gives it (at most 2000 characters), waking the parent if it is idle; when
the child has messaged the parent without a status since its last prompt, the notice says so. The
parent decides: message the child with `courier_send` to have it carry on, or to report if its last
reply is what it needed, or start a replacement. Until the child reports, it counts toward the
[limits](#session-trees-and-their-limits). One notice is sent per turn's end, however many instances
and copies of the plugin see it; if it cannot be delivered, the parent is taken to be still waiting.

A turn that ends while the child waits is not reported. It waits while a session it started owes it a
report that it has not been told about; while it has a permission request or a question pending; and
while a `courier_later` message for it is pending, or it has subscribed to a webhook topic since its
last prompt. A subscription made before the last prompt is not waiting, since it outlives the delivery
it was made for: once a delivery has come and the child has ended its turn again without reporting,
its parent is told. A turn stopped by OpenCode's
shutdown resumes on the next start and does not count as interrupted; one stopped otherwise (by the
person, or by OpenCode after an hour without activity) settles the report and is not told.

The state is kept in the plugin's storage, so a restart does not lose it. It goes with the child's
roster entry, and when OpenCode deletes the session; deleting a session drops that of the sessions it
started too. What the plugin cannot see, it cannot judge: a prompt delivered while the server is down
or the plugin not loaded leaves the earlier one in place, so a turn after it that ends without a
report may not be told, and a `courier_send` whose note could not be written is taken for no report.

## A missed wake

A report, a notice or a scheduled message reaches its session through OpenCode's inbox, and OpenCode
starts a turn for it when the session is idle, except one sent with `resume: false`, which waits for
the session's next turn. How the wake can be lost is in [the maintainer
notes](maintainers/plugin-api-notes.md#events). So the plugin watches every message it delivers (each
inbox item whose metadata has `source: "courier"`, except the ones sent with `resume: false`, such as
the note that a [permission request was answered elsewhere](#a-child-that-asks-for-permission)) from
the moment OpenCode enqueues it until it is delivered or cancelled, noting whether its session runs a
turn: a running turn takes a steered message at its next step, and a message queued while it runs is
taken when it ends. A message that has waited in an idle session for 30 seconds is a missed wake: the
scheduler sends it once more under the same inbox id, which OpenCode takes for the message already
waiting, not a second one, and wakes the session; if a turn has taken the message meanwhile, nothing
is sent. A session that still has not taken it 30 seconds after that is stalled: the plugin logs it,
the [footer](#in-the-terminal) counts it (`courier 1 stalled`, the open session itself included), and
the tree panel shows its row as `stalled`, with since when its message waits. Prompting the session
delivers the waiting message with the prompt, which ends the stall. Nothing is sent a third time, and
nothing at all to a session `courier_stop` stopped, whose watch it drops.

The scheduler checks every 15 seconds, so a wake is sent again 30 to 45 seconds after the session went
idle with the message waiting, and flagged stalled up to 45 seconds after that. Only the server that
holds the scheduler's [owner key](#two-servers-on-one-data-directory) sends it, once per message. The
footer and the panel ask again every 15 seconds on top of the events they follow, as a stall is found
by the scheduler with no event of its own. The watch is kept in the plugin's storage, and goes with
the message's delivery or its session's deletion.

## A child that asks for permission

When a child's tool call needs an approval (a permission rule with `"effect": "ask"`, or no rule for
it), OpenCode holds the call until someone answers in the child's session. For a spawned session the
plugin sends the parent a message from that child, marked `asks="permission"` and `request="<id>"`,
steered into its running turn or starting one if it is idle. The message says what the child asks
for (the action, such as `shell` or `edit`, and its resources) and tells the parent that it cannot
decide this, you do, in OpenCode's own permission prompt, which opens in the parent's session once
the parent proposes an answer with `courier_answer { sessionID, requestID, reply, message? }`:

- `once`: allow this request only. `courier_answer` first calls OpenCode's `permission.assert` in the
  parent's own session with the child's request as OpenCode received it, its action and resources,
  and nothing to save: OpenCode checks the parent's permission rules and, when they say ask, shows you
  its own permission prompt there (and on the paired app's dock), bound to the `courier_answer` call
  and carrying the child's session and request id in its metadata. The call returns only once you
  have answered, and `once` is passed on to the child only when you allowed it. A rule that allows
  the action in the parent's session passes without a prompt; a rule that denies it refuses it
  without one.
- `reject`: refuse it, with a reason if there is one; passed on as it is.

The parent is told to propose `once` unless you have told it to refuse, or the request plainly goes
against what you asked of it, and not to ask you first. Nothing the parent's model writes counts as an
approval. In the prompt, *Allow once* passes `once` on, and the child carries on; *Reject* with a
reason, or a deny rule in the parent's session, fails the parent's `courier_answer` with that reason
and refuses the child's request with the same reason, so the child's call fails and it carries on; a
plain *Reject* ends the parent's step, as it would for the parent's own tool call: `courier_answer`
gives no result, and the child's request waits on, for you to answer in the child's session, in the
[asks inbox](#the-asks-inbox), or through the parent once you prompt it again.

`always` is not offered through `courier_answer`, and it refuses it: `permission.assert` says nothing
about whether you chose *once* or *always*, and an `always` there would save a standing rule for the
parent's whole project. A standing rule for the child is granted where OpenCode's own prompt shows
the child's request: in the child's session, in the asks inbox, or in the top session's view with
[`nativeChildren`](#native-child-sessions) on.

A request of a child's child goes to the session at the top, down any number of levels; the message
names the session that started the asking one. Only that top session can answer it: a session started
with `courier_spawn` cannot answer what its own children ask, so it cannot get around a rule that
makes it ask by starting a child to do the job and approving it, and since the top session's own
rules are checked before anything is passed on, it cannot approve for a child what it may not do
itself.

OpenCode ends the child's turn when a request is rejected without a message, so `courier_answer`
always sends a message with a rejection, the person's reason or a default one; the child's call fails
and it carries on, and can report. The child's model is told that the call could not be run, not the
reason.

A request can also be answered without the parent: in the child's own session (for a [native
child](#native-child-sessions), in the view of the top of its native tree), or along with another
answer (an `always` that covers it, or a rejection, which rejects the session's other pending requests
as well). For a request the parent was told about, the plugin then sends it a short message marked
`answered="<reply>"` saying the request is settled; after a rejection, the message adds that the child
may have stopped, and that `courier_send` gets it going again. That message is sent without waking
the parent (`resume: false`): it waits in the parent's inbox and is read with the parent's next turn:
for a direct child usually its report or the notice that it ended without one, further down a tree or
for a member of a join group the next message that reaches the top session, or your own prompt. So a
request answered elsewhere starts one turn in the top session, for the request, not a second one for
the answer; the [missed-wake watch](#a-missed-wake) does not count the notice as owed a turn. A `courier_answer` that comes later anyway
passes nothing on and says so, as does one whose request was answered that way while you were being
asked in the parent's session; the prompt there stays open until you answer it, and allowing it then
passes nothing on. The TUI's [asks inbox](#the-asks-inbox) answers as you, through OpenCode's reply,
never through `permission.assert`, so the parent hears the same.

`courier_status` and `courier_children` list the requests a session waits on under `pending`, so a
parent that has lost the message, after a compaction for example, can still find them. Whenever the
plugin starts following OpenCode's events again, after loading or after its event stream broke, it
also relays the requests that spawned sessions already wait on.

## A child that shows a form

OpenCode asks some things through forms of its own, shown in the child's session only. The one a
child meets most is web search: the first `websearch` call made while no search provider has been
chosen shows a "Web Search" form (allow search through the providers OpenCode has, choose another
provider, or disable web search), and a second one, "Choose a web search provider", if the person
picks another. The plugin API has no way to answer or withdraw a form; only the person can, in the
child's session. So for a form of a spawned session the plugin sends the session at the top a
message from that child marked `asks="form"`, `form="<id>"` and, when the form says what it is for,
`kind="<kind>"` (`kind="websearch.provider"` for web search), waking it if it is idle. The message
gives the form's title, its fields and their choices, and says that only the person can answer it,
in that child's session, or, for a [native child](#native-child-sessions), in the session whose view
OpenCode shows it in, which the message names. A form of a child's child goes to the top session,
naming the session that started the asking one.

For web search the message adds what OpenCode does next: it waits for the choice at most a minute,
then the child's search fails with "Web search cancelled", and the child carries on without it. The
choice is kept for every session (OpenCode stores it globally), so once it is made, in any session,
no session is asked again: answer in the child's session, run one web search in your own session and
answer there, or pick the provider under OpenCode's "Third-party search" setting.

Once a form the parent was told about is answered, or withdrawn unanswered (dismissed, given up on
after OpenCode's minute, or cut off with the child's turn), the plugin sends a short message marked
`settled="answered"` or `settled="cancelled"` and `form="<id>"`. The TUI's [asks inbox](#the-asks-inbox)
lists and answers such forms, and the parent hears the same. The question tool's forms are not told
this way: [the question relay](#a-child-that-asks-a-question) passes every question of a spawned
session on. Forms of sessions the plugin did not spawn are ignored, among them MCP servers' requests
for input. The plugin cannot list the forms a session shows, so `courier_status` does not report
them; a form shown while the plugin was not following OpenCode's events is not told, and one settled
then, or across a server restart, is not told settled.

## A child that asks a question

A child that calls OpenCode's question tool shows its question in its own session only. The plugin
wraps that tool, and once the question of a spawned session is on screen, it sends the session at the
top a message from that child marked `asks="question"` and `request="question_<id>"`, waking it if it
is idle. The message lists the questions and their options, gives them again as one line of JSON in
the question tool's own input shape, and tells the parent to ask the person, with its question tool
and exactly those questions, rather than answer.

When the parent asks you the same questions with the same options, the two are linked: what you pick
in the parent's session is passed to the child's waiting call, which returns it as if you had answered
there, and the child carries on in the same turn; the parent's tool result says so. Only the same
wording links (spacing and case aside; the options may come in any order); when a waiting question
has the same choices as one of the parent's own, the parent's tool result says the answers were not
passed on and names the request. A parent that asked you some other way calls `courier_answer {
sessionID, requestID, answers }`: one entry per question, in order, each the label you chose or the
text you gave, or a list of labels where a question allows several. Only the session at the top can
answer. Answers to one question are passed on once: a second waits for the first, and is told the
question no longer waits once the first got through.

The question stays in the child's session too, and whichever answer comes first counts; the other
side's question is withdrawn. Answered or dismissed in the child's session, the parent's open question
disappears and its tool result says why, or, with none open, the parent gets a short message marked
`answered="elsewhere"` or `answered="dismissed"` (or `answered="failed"`, when the child's question
call failed, which ends its turn too); a dismissal there ends the child's turn, as OpenCode's question
tool does, and the message says to `courier_send` it if it should carry on. Answered in the parent's
session, the child's question disappears. Dismissed in the parent's session, the parent's turn ends,
and the child's call returns that you dismissed the question, so the child carries on without the
answer and can report. Answered with `courier_answer` while the parent's question is open, the
parent's question disappears, and its tool result names the answers that went to the child. A
dismissal on either side reaches the other about two seconds later: OpenCode withdraws open questions
the same way when it shuts down, and the plugin waits that long to tell the two apart.

A question whose call is cut off stays answerable. When the child's turn is stopped (interrupted, or
by OpenCode after 60 minutes without activity in the project location), or the server restarts or
closes the project, the question is gone from the screen. The plugin keeps it in its storage, sends
the parent a message marked `stopped="true"`, or `restarted="true"` when the plugin is next loaded,
with the questions, and passes the answer on as a message to the child, which wakes it. If the parent
is asking you at that moment, your answer goes that way without a new message. Stored questions are
dropped after 14 days, once the child is off its parent's roster, or beyond the 100 newest.
`courier_status` and `courier_children` list a session's questions under `pending`, with
`type: "question"`, the questions, and `stopped: true` for one that was cut off. With
[`nativeChildren`](#native-child-sessions) on, a native child's question is not linked: the person
answers it in OpenCode's own form, and the top session is only told.

A question is relayed only once OpenCode's permission check for it has passed: a child whose agent may
not ask questions (OpenCode's `general` agent, or a `question` rule with `"effect": "deny"`) is
refused as before, and the parent hears nothing. A child can still send its question with
`courier_send` instead, and the parent then passes your answer back with `courier_send`. The TUI's
[asks inbox](#the-asks-inbox) answers a question as `courier_answer` does; the top session hears it as
a question settled without it, *answered by the person*.

## Roster

`courier_spawn` records each child under its parent in the plugin's storage, so a parent that has lost
track after a compaction or a server restart can call `courier_children` to find them again; a child
that can no longer be looked up is still listed, with the error instead of its state. The roster is
also where a session's depth and tree are read from, for the [limits](#session-trees-and-their-limits).
Whether a child [owes its parent a report](#a-child-that-ends-without-a-report), and its place in a
[join group](#join-groups), are kept next to it, and dropped with its entry. A child deleted in
OpenCode is forgotten at once, unless it is isolated or has children of its own on the roster
([worktree cleanup](#worktree-cleanup)). Other entries are dropped 14 days after the child was
started, when `courier_children` reads that parent's roster or the plugin is next loaded, except
isolated children whose worktree is still there; every other read of a tree (`courier_tree`, the
[terminal part](#in-the-terminal)) leaves such entries out, and what is under them, without dropping
them. Loading the plugin also removes, best-effort, report state whose session has no entry left. If
the roster cannot be written, the child still gets its task and `courier_spawn` says it is not on the
list.

## Memory

The [roster](#roster) forgets its children in 14 days and keeps nothing of a tree as a whole. So the
plugin keeps **one record per session tree**, written from facts it already has. The one thing a
model writes into it is the tree's [lesson](#the-lesson), one line, from the session that verified the
tree.

**One record per tree, per project.** A tree is the session nobody spawned, its top, with every
session started under it. Its record is kept under the storage key `memory/<projectID>/<topSessionID>`,
where `projectID` is OpenCode's id of the project the top session runs in (`location.project.id`,
which every worktree of a repository shares). It is written again, whole, each time a turn ends in
the tree: when a spawned session's turn succeeds, fails or is interrupted (not by a shutdown), and
when the top's own turn ends, once it has started a session or called `courier_recall`. The refresh
reads the roster's subtree under the top, each session's info and its [report
state](#a-child-that-ends-without-a-report), and stored messages only where they can have changed: a
part's `context` and `refused` are read from its messages when its own turn ends or it is first seen,
and kept from the last refresh otherwise, and the top's, for its `split` and `revisions`, on its own
turn ends and while the record states no split line yet (`not stated`, or only a mention). Another session's turn end
reads only the top's finished replies (`time.completed` set), so a line the top is still writing waits for its
own turn end. It runs through the plugin's event follower, so whichever
instance follows OpenCode's events writes it, once. A session the roster has forgotten since keeps the
state it was last recorded in, so the record stands on its own once the roster is gone, unless it had not
settled and OpenCode no longer knows it (below).

**A session OpenCode no longer knows** (deleted, so `session.get` answers `Session.NotFoundError`)
cannot settle any more, and its report state went with it. Its part keeps its last recorded title,
duration, cost and context use, rather than a duration measured to each refresh. Its status is the
one its report state still reads, when that has settled; else its last recorded status, when that had
settled; else `gone`, which counts as settled. So a deleted session never holds its tree at `not
finished`, as the [tree panel](#in-the-terminal) draws it `gone` and not live. This applies to a part
still on the roster (an isolated child's entry stays after its session is deleted, for its worktree)
and to one the roster has forgotten while it was `out` or `stalled`, whose session each refresh looks
up until it is gone or settles. A session that cannot be read for another reason keeps its last
recorded title, duration and cost too, its status read as usual, and nothing is settled for it. A
`gone` status, rather than keeping the last one alone, is what lets a session deleted while it ran,
whose last status was `out`, still let its tree finish; one that had reported keeps what it reported.

**What a record holds.** The value is one JSON object; every time is in epoch milliseconds and every
duration in milliseconds:

| Field | Holds |
|---|---|
| `startedAt` | When the top session was created. |
| `movedAt` | When a turn in the tree last ended, or the record was first written by `courier_recall`. |
| `title` | The top session's title, as OpenCode has it at the last refresh. |
| `split` | The top's split line, the first line of its replies that states one (`split: no, because …` or `split: <n> parts: …`, read as the real-model checker reads it: a line beginning with `split:` after any markdown, else one holding it), kept as written, markdown included, or `not stated`. A stated line takes precedence over a mention: while `split` only holds `split:` (`I'll decide the split: after reading the code`), the first line beginning with it replaces the mention, once, and the mention is dropped rather than kept as a revision. A record written before this rule kept the stated lines as revisions beside the mention: when the line found is among them, the first of them, stated first, becomes `split` instead and the rest stay. A stated line is never replaced, even when compaction has dropped the reply that stated it. |
| `revisions` | Absent until the top states a second split line worded otherwise; then the later lines, newest last, the newest 3 kept: `[{ "text": "split: 2 parts: its tests, its docs", "at": …, "parts": 1 }]`. Only a line beginning with `split:` after any markdown counts, not a passing mention, and it is appended when its words, markdown aside, differ from the line recorded last (the last revision, else `split`), so a line repeated or only restyled appends nothing, and neither does reading the same replies again. `text` is the line as written, `at` when its reply was created (the refresh's time when the message has none), and `parts` how many parts the tree had at that refresh, which tells a second stage after the first landed from a rewording before any work. A revision whose reply compaction has dropped is kept. |
| `finished` | Whether, at the last refresh, no session in the tree ran (by the same rule as the limits' `busy`) and every part had settled: none was `out` or `stalled` (a `gone` one has). A tree whose top is still integrating reads as finished until that turn ends, and one with no parts as soon as its top is idle. |
| `recalled` | Absent until `courier_recall` was called from the tree; then `{ "calls": <n> }`, counting every call made from the top and its parts, with `"at"`, when the top itself first called it. |
| `lesson` | Absent until `courier_note` wrote one; then `{ "text": …, "at": … }`, with `"depth"`, the writer's depth in the tree, when a sub-orchestrator wrote it. A second note replaces the whole object. |
| `reads` | Absent until another tree's `courier_recall` listed the record or gave it in full; then `{ "shown": <n>, "read": <m>, "at": … }`: how often a listing included it, how often it was given in full, and when one last did. A call from the tree's own sessions counts nothing, nor does a look from the [memory view](#the-memory-view). Kept [beside the record](#what-lies-beside-a-record), per reader tree, never in its value. |
| `pinned` | Absent until the person pinned the record in the [memory view](#the-memory-view); then `{ "at": … }`, when. A pinned record is listed first and never swept. Kept [beside the record](#what-lies-beside-a-record), never in its value. |
| `parts` | One object per session started in the tree, in the order the tree is drawn (each followed by what it started, siblings oldest first). |

Each part:

| Field | Holds |
|---|---|
| `sessionID` | The session. |
| `title` | Its title, as OpenCode has it, else as `courier_spawn` recorded it. |
| `depth` | 1 for a session the top started, 2 for one of theirs, and so on. |
| `isolated` | Whether it runs in a worktree of its own. |
| `group` | Its [join group](#join-groups), when it was started in one. |
| `status` | `done`, `partial`, `blocked` or `failed`: the status of its last report, once it owes none; `failed` also for a turn that failed, `interrupted` for one interrupted, `stopped` once `courier_stop` stopped it since its last prompt, `gone` once OpenCode no longer knows its session and it had not settled ([above](#memory)), `stalled` while a message it does not take [waits in its inbox](#a-missed-wake), and `out` while it owes its parent a report, or nothing is known of its report state. |
| `duration` | From its start to the end of its last turn, or to the refresh while it runs; as last recorded once its session cannot be read, and absent when it never was. |
| `cost` | What its session cost so far, as OpenCode counts it, in USD. |
| `context` | How full its context was at the end, from 0 to 1, as the [tree panel](#in-the-terminal) reads it. Absent when the window is not known. |
| `refused` | How many of its own `courier_spawn` calls failed, refused by a [limit](#session-trees-and-their-limits) mostly. Absent when none did. |

The record never holds a report's body or artifacts, nor a session's replies: they can hold code and
secrets, and the parent has verified the work.

#### What lies beside a record

The record's value is written whole, by a refresh, `courier_recall`'s note of a call, `courier_note` and
a forget of the lesson, each after reading it; the plugin's storage has no compare-and-set, so two
writers of one key can lose each other's write. What others write of a record therefore lies beside
it, under its key, each key with one writer:

| Key | Holds | Written by |
|---|---|---|
| `memory/<projectID>/<topSessionID>/pin` | `{ "at": … }`, when the person pinned the record. The key's presence pins: any value under it is read as a pin, dated 0 when it names no time. | The [memory view](#the-memory-view)'s `p`, through the `pin` RPC, which removes the key to unpin. |
| `memory/<projectID>/<topSessionID>/reads/<readerTopSessionID>` | `{ "shown": <n>, "read": <m>, "at": … }`: how often `courier_recall` calls from the tree under `readerTopSessionID` listed the record, how often they gave it in full, and when one last did. A count missing is 0; an entry without `at` counts nothing. | The reader tree's sessions, one key per reader tree, so two trees' calls never write one key. |

Reading the record merges them in: `pinned` as the pin key has it, `reads` as every reader's counts
summed with the latest `at`. Writing the record leaves them out, whatever the value given, so no
refresh or note can write over a pin or a count, and two listings from different trees cannot lose
each other's. Two calls from the same tree in the same instant can lose one count, which is harmless.
Forgetting the record removes the record with what lies beside it, and so does the sweep; a pin or
reads left beside a record removed meanwhile are dropped at the next load. A pin can be seeded by
hand for a test as the record can: `bun e2e/kv.ts set 'memory/<projectID>/<topSessionID>/pin'
'{"at": 1760000950000}' '<a key the plugin stored>'`.

A record can be written by hand, for a test or to seed what the plugin would have recorded, with
`e2e/kv.ts` against a running test server (the fourth argument names a key the plugin has stored, so
the tool finds the plugin's prefix): `bun e2e/kv.ts set 'memory/<projectID>/<topSessionID>' '<json>'
'<a key the plugin stored>'`. Missing fields take their defaults (`not stated`, `false`, empty, `out`),
a part without a `sessionID` is left out, and a value without `parts` is not a record. A `lesson` may
be written as a bare string, which is read as one dated `movedAt`; an object without a `text`, or an
empty one, is no lesson, a `depth` that is not a positive integer is dropped, and a text over 300
characters is clipped when read. A revision without a `text`, an integer `at` or a `parts` that is a
non-negative integer is left out, and of more than 3 the newest are kept. One as the plugin writes it:

```json
{
  "startedAt": 1760000000000,
  "movedAt": 1760000900000,
  "title": "Add memory to courier",
  "split": "split: 3 parts: core, e2e, docs",
  "finished": true,
  "recalled": { "at": 1760000001000, "calls": 1 },
  "lesson": { "text": "The docs part was ten lines; next time do it yourself.", "at": 1760000890000 },
  "parts": [
    { "sessionID": "ses_core", "title": "Core", "depth": 1, "isolated": true, "group": "wave", "status": "done", "duration": 540000, "cost": 0.42, "context": 0.31 },
    { "sessionID": "ses_e2e", "title": "E2E scenario", "depth": 1, "isolated": true, "group": "wave", "status": "partial", "duration": 600000, "cost": 0.81, "refused": 1 },
    { "sessionID": "ses_review", "title": "Review", "depth": 2, "isolated": false, "status": "done", "duration": 60000, "cost": 0.05, "context": 0.12 }
  ]
}
```

**`courier_recall { sessionID? }`** reads the records back, from any session. Without `sessionID` it
lists every record of the calling session's project, the [pinned](#what-lies-beside-a-record) first and
then newest first, one line each:

```
- ses_old 2026-10-03: "Add memory to courier" · split: 3 parts: core, e2e, docs · 3 parts: 2 done, 1 partial, 2 levels deep, 2 isolated, 1 spawn refused · ran 42 min · last moved 5 days ago · $1.28 · finished · lesson (2026-10-03): "The docs part was ten lines; next time do it yourself."
```

the top session, the day it started, its title (clipped to 60 characters), its split line as prose
(below), then its latest revision, when the top stated another, as prose too and after how many parts
it was stated (`then, after 1 part: split: 2 parts: its tests, its docs`), its parts counted by status, how deep the tree went, how many parts were isolated and how
many spawns were refused, how long the tree ran (`ran`, `movedAt` less `startedAt`), how long ago it
last moved (`last moved … ago`, now less `movedAt`: a duration under a day, else whole days), the parts' costs
summed when any is known, `finished` or `not finished`, `pinned` when the person pinned it, `recalled` when the top called the tool (`recalled by a part`
when only a part did), and last its [lesson](#the-lesson), when there is one, with the day it was
written and `from depth <n>` when a sub-orchestrator wrote it. The caller's own tree is listed too,
marked `(this tree)`. When a pinned record is among the others, the listing's first line adds that a
record marked `pinned` is one the person chose to keep, listed first, to weigh before the rest. The
line does not show a record's `reads`: they are for the person pruning, not for the model deciding a
split. With `sessionID`, the top of a listed tree, it gives that record in full, as JSON, `reads` and
`pinned` included; a top with no record in this project is said to be missing. Its result's metadata
carries the records.

**The split line as prose.** The record keeps the top's line as written; the listing drops what is
markdown in it and keeps what may be its words:

- heading, quote and list marks before it (`# `, `> `, `- `, `1. `), each with its space, so the `#`
  of `#282` stays;
- the asterisks of a bold or italic span around the whole line or around words in it, where an italic
  one opens before a letter, digit or quote, so the asterisks of `*.ts and *.md`, `src/*.ts` and
  `2 * 3` stay;
- underscores or a code span around the whole line, or around a label it opens with (`_split:_`,
  `` `split:` ``), so `snake_case`, `__init__` and code spans within the line stay;

and cuts it at the last space within 160 characters, or mid-word when that would keep less than half.

Every fact on a line is as it stood at `movedAt`, so `not finished` with `last moved 3 min ago` is a
tree that may be running, and with `last moved 5 days ago` a record to distrust. The
[memory view](#the-memory-view) leaves the age out: it groups its rows by the day each last moved, and
a dialog left open would not keep an age current.

Every call is noted on the record of the caller's own tree: `calls` counts up, and `at` is set the
first time the top itself calls. A tree that has no record yet, a root before its first spawn, gets
one from the call, with no parts and `split` not stated, so a decision not to split is remembered with
the call that preceded it. The tool is one look, not a loop: the
[skill](#the-courier-orchestrate-skill)'s first step asks for one call before the split decision, the
[root's pointer](#session-trees-and-their-limits) names it, and the real-model checker
(`e2e/real-model-recursive.mjs`) allows a root exactly one call before its first spawn, counting any
other as polling. A leaf's requests go without the tool.

Every call is also counted on the records it reads of other trees, [beside each](#what-lies-beside-a-record):
a listing counts one `shown` on every record it includes but the caller's own tree's, and a record
given in full counts one `read`, which the record given already holds. The caller's own record is
never counted: its lesson reaching its own tree is not the signal. The counts are written after the
records are read, best effort: a count that cannot be written is logged and the call still answers.
The [memory view](#the-memory-view) shows them, so a person pruning can tell a lesson other trees
still read from one nobody does.

### The lesson

A record says what happened; it cannot say what the orchestrator concluded. **`courier_note { text }`**
writes that, as the one `lesson` of the caller's own session tree, on the record under its top: one
line, at most 300 characters (whitespace and line breaks collapse to spaces), dated when it was
written. The tool and the skill ask for what the next orchestrator should know about running a tree
like this one, and for the job it comes from and the reason in the same line, so that "no split
needed, for three 20 s one-liners" can be told from a lesson that applies everywhere. A longer line is
refused, not clipped ("Not noted: the lesson is 312 characters, at most 300; write it shorter."):
nothing is written and the earlier lesson stays, since a stored lesson is read by every later tree and
a line cut mid-word stays cut. The result says what was noted and what it replaced: a second note
replaces the first, whole, so the orchestrator writes it last, once it has verified and integrated the
work, in the skill's step 8. `courier_recall` lists it after the tree's facts.

Who may write it: the top session, or a sub-orchestrator below it, whose note goes on the same record
marked with its `depth`. A leaf cannot: the tool is refused there (naming the depth and `maxDepth`)
and hidden from a leaf's requests, and the [brief](#session-trees-and-their-limits) does not mention
it. It is also refused with an empty text, with one over 300 characters as one line, from a session
whose tree has no record yet (a root notes after its first recall or once a session it started has
reported) and when the [option](#memory) is off; each refusal is the tool's failure, and writes nothing.

What a lesson is not: a rule. One that holds every time belongs in AGENTS.md or the skill, which only
the person puts there; the tool's description and the skill say so. Nor code or secrets: the record is
read by every later session in the project.

**Retention.** A [pinned](#what-lies-beside-a-record) record is never dropped, whatever its age, and
sits outside the cap. Of the rest, each project keeps 30, those with a lesson before those without and
within each the newest by `movedAt`, and none that last moved more than 90 days ago; the others are
dropped when the plugin loads, with what lies beside them. So once a project has more than 30 trees
in 90 days, a record that holds only facts goes before one that holds a lesson, and a lesson the next
orchestrator should still read after 90 days is kept by pinning it. The one cost: in a project with
30 lesson-bearing records within 90 days, a load drops the newest records without a lesson, a tree
running at that moment among them (its lesson comes last); its next turn end writes its record
again, from what the roster and OpenCode still hold. Nothing else removes a record.

**The option.** `"memory": false` in the plugin's `options`, read per instance like the limits, turns
it off: no record is written for a tree whose top runs in that location, `courier_recall` says the
option is off and writes and lists nothing, and `courier_note` is refused. Any other value than `true`
or `false` is logged and taken as `true`. With [two servers](#two-servers-on-one-data-directory) on
one data directory each writes records by its own option.

**In the terminal.** `/courier memory` lists the project's records, pins one and forgets one, or only
its lesson: [the memory view](#the-memory-view). A look from the terminal is noted on no record.

## Seeing and stopping a subtree

**`courier_tree`** lists the sessions under the calling session, or under `sessionID`: those it
started with `courier_spawn`, and those they started, and so on, at most `maxTotal` of them: the live
ones first (running, waiting on a request, or [owing a report](#a-child-that-ends-without-a-report)),
then the newest, each with the sessions above it, so a cut takes only the oldest finished ones. Past
that the result says `truncated` with how many older sessions were left out. The result is flat, in
the order a tree is drawn (each session followed by what it started, siblings oldest first). Each
entry is what `courier_children` shows (`sessionID`, `title`, `outcome`, `lastText`, `pending`,
`directory`, `isolated`, `created`, and `group: { name, report }` for a member of a join group) plus:

- `parentID` and `depth`: 1 for a child of the session the tree is read from;
- `report`, when its report state is known: `owes` (it has been prompted since it last reported,
  failed or was interrupted), `progressed` (it messaged its parent without a status since its last
  prompt), `ended` (its turn failed or was interrupted since) and `status` (the status of its last
  report).

Anyone can read any session's tree, as with `courier_children`.

**`courier_stop { sessionID, cleanup? }`** stops a session and every session under it:

1. Only a session above the target may stop it: the calling session must be one of the sessions that
   started the target, directly or through others, so a session cannot stop itself, a sibling or a
   parent, and one `courier_spawn` did not start cannot be stopped.
2. Every session in the subtree is marked stopped and the `courier_later` messages scheduled *for*
   them are cancelled, before any interrupt. Messages they scheduled for other sessions, and webhook
   subscriptions, are left alone.
3. They are interrupted level by level, deepest first, the level's sessions at once. A session that
   does not run says `idle` and nothing else happens to it; one OpenCode no longer knows says `gone`,
   and one whose interrupt failed says `failed` with the error and may still run, while the others
   are stopped regardless. The subtree is then read again, up to three times, for a session one of
   them started meanwhile.
4. With `cleanup: true`, the worktrees of the stopped sessions that ran in one of their own are removed
   deepest first by the rules of [`courier_cleanup`](#worktree-cleanup), without `force`: one with
   uncommitted changes or commits on no branch is kept and listed in the result, and one that fails is
   listed with its error.

The result lists every session stopped, deepest first, with its outcome, the ids of the messages
cancelled, and the worktrees.

**Who is told.** An interrupt settles the session's report and takes a member out of its join group.
The failure and the silent-end notices stay quiet for a session stopped since its last prompt; a
session prompted again after a stop is judged as any other.

- The calling session is not told of what it stopped.
- The parent of the target is told once, `ended="stopped"`, when it is not the caller. The notice says
  it was stopped by a session above, and is not a failure. It is not sent when the target did not run.
- Sessions under the target are not told: their parents are stopped too.

A stopped session is not forgotten: it stays on the roster and in `courier_tree`, can be messaged with
`courier_send` (which prompts it again, and it owes a report again) and is removed by `courier_cleanup`.
A session of the subtree that a running turn of its own starts between the first look and the last
cannot be stopped.

## In the terminal

The package has three entrypoints: the server plugin (`opencode-courier`), a TUI part
(`opencode-courier/tui`) and its RPC contract (`opencode-courier/rpc`). The server runs only the
server plugin and lists the others as features in `GET /api/plugin` (`features: { server: true, tui:
true, rpc: true }`); the TUI loads the TUI part for a plugin with that feature. Courier without a TUI
attached behaves the same. What the TUI part does, answering an ask, stopping a session or forgetting
a tree's record, goes through the same paths as `courier_answer`, `courier_stop` and the memory's
store, so a model sees only what those would tell it.

**The status entry.** In the prompt's footer, for the open session:

```
courier 1 waiting on you · 2 running · group pair 1/2 · 1 idle
```

The parts come in that order; on a narrow terminal the entry keeps as many whole parts as fit,
replacing the groups it drops with a count (`+3 groups`). `waiting on you` is always shown, and
`stalled` comes right after it. It counts every session under the open session (those [past
retention](#roster) left out), each by what it does:

- `waiting on you`: it waits on a permission request or a question (`courier_status`'s `pending`), or
  its running turn shows a form; the [asks inbox](#the-asks-inbox) lists all three;
- `stalled`: a message the plugin delivered waits in its inbox, and sending it again did not start a
  turn ([a missed wake](#a-missed-wake)); the open session itself is counted too;
- `running`: its turn runs, or something reached it after its last turn ended, and it waits on no
  request, shows no form and is not stalled;
- `idle`: neither.

A session OpenCode no longer knows is not counted. Then, for each join group of the open session's
own children still open, `group <name> <reported>/<members>`: the members whose report is held out of
those that have not left. A part that is zero is left out; the entry shows nothing on the home
screen, for a session that started none, and when the RPC fails. It asks again 250 ms after the first
of the events that may change it (a session created or deleted, a turn started or ended, a permission
request asked or answered, a form created or settled, a message delivered), once per burst, and every
15 seconds besides. A server that cannot register the RPC logs `courier rpc: not registered` and
loads the rest as before.

**The tree panel.** `/courier tree` (or *Courier session tree* in the command palette) opens a panel
beside the open session (fullscreen when the terminal is too narrow to split, under 108 columns less
any vertical session tabs): `courier_tree` for people, the same listing, two spaces deeper per level;
past `maxTotal` the header says how many older sessions are left out:

```
 █▀██▀██  courier tree  [█████░░░░░] 1/2 reported
▄▀▀▀▀▀▀▀  1 waiting on you · 1 idle
▸ ✓ Report back to your parent.  idle · reported done · group pair held
    ran 12s · last courier_send 3s ago · $0.00
  ● CHILD-ASKS  waiting on you · owes a report · group pair out
    asks permission: shell echo courier-asks
↑↓ select · enter open · s stop · r refresh · f fullscreen · q close
```

Each row: the session's title, then what it does (`running`, `waiting on you`, `idle`, `stalled`,
`failed` or `interrupted` for an idle one whose last turn ended so, `stopped` for one `courier_stop`
stopped since its last prompt, `gone` for one OpenCode no longer knows), its report since its last
prompt (`owes a report`, `reported <status>`, `ended without a report`; nothing for a session spawned
before report notes were kept), its join group's standing (`group <name> held`, `out`, how it left,
or `released`), and `isolated`. A one-cell mark before the title shows the state in the person's
theme: `✓` reported (success), `•` running (info; a spinner while the panel animates), `●` waiting on
you (warning), `!` stalled, `✗` failed or interrupted (error); an idle one that owes a report, and a
gone one, have none. Under the row: an orchestrator gets a bar of the parts reported (only reports
courier noted); a session waiting on the person one line per request, then one per form (`asks
permission: <action> <resources>`, `asks: <its first question>` or `shows a form: <its title>`); a
stalled one `a message waits in its inbox since <how long>, woken again in vain`; a leaf how long it
ran, its last tool call and how long ago, its context use (`ctx 31%`, in the warning colour past 80%;
the last assistant message's usage since the last completed compaction over the model's context
window, as OpenCode's own session view reads it; left out when the window is unknown) and its cost.
The panel asks again a second after the first of a burst of the status entry's events and of a tool
call, a usage update or a rename, and every 15 seconds besides, and redraws its times every second.

**What moves**, on one timer for the whole panel, a frame every 90 ms, which runs only while one of
them has a next frame: a running row's spinner; a flash of the theme's success background, fading
over 1.5 s, on a row whose report arrives; the header's bar easing to its new length over about half
a second; and Digby, every fifth tick. The `waiting on you` mark stays still, and nothing in the
footer moves. With `"animations": false` in the TUI part's options none of them do: a running row
shows `•`, a report does not flash, the bar takes its length at once, Digby shows each state's first
frame, and no timer runs. The TUI passes a plugin options only from its own config's `plugins`
(`~/.config/opencode/cli.json`); a plugin it loads from the server's list gets none of the server's
`opencode.json` options, and the TUI's own `animations` setting is not on the plugin API:

```jsonc
// ~/.config/opencode/cli.json
{
  "plugins": [{ "package": "opencode-courier", "options": { "animations": false } }]
}
```

**Digby.** The courier's mole digs beside the header's title, 8 columns by 2 rows in half-block
pixels, coloured only from the theme: body in the base text colour, eyes in the background, the mound
in `background.raised.max`, paws, dirt and arm muted, snout and letter in the accent
(`text.action.primary.selected`, which the header's title and bar take too), and the sign, dots and
spark in the warning, error and success colours. His state follows the tree's, by the footer's
priority: a breathing mound while all is idle, a trembling one while children run, up with a
blinking sign while one waits on you, slumped with an ellipsis while one is stalled, muted and still
when every session is gone; for 1.5 s after a report he pops up with the letter, and after a spawn
small mounds rise either side. A panel under 12 rows tall or 54 columns wide has no glyph. A larger
Digby, 16 by 8, shows the same states instead on an empty panel at least 14 rows tall, or below the
last row when at least 10 rows are free. The poses are in `src/tree/mascot.ts` (`ART`), the colours
in `digbyColours` in `src/tree/tui.tsx`; the muted pixels never touch the mound's, as
`background.raised.max` is close to `text.muted`.

**Keys**, while the panel has the keyboard (it takes it when it opens; `<leader>left` and
`<leader>right` move it between the session and the panel): `↑`/`k` and `↓`/`j` move the selection,
`enter` opens the selected session, `s` stops it, `x` forgets a `gone` one, `r` asks again, `f`
toggles fullscreen and `q` closes the panel. A click (the left button down and up on the same row)
selects the row and opens its session; a drag and any other button open nothing. A row under the
pointer is highlighted with `background.raised.base`, one step below the selection's
`background.raised.high`; the highlight never moves the selection, so `s` and `x` act on the selected
row. While open, the panel follows the person to another session, as it was asked for and taking the
keyboard only if it had it: to a session of its tree it keeps that tree, with the session on screen
marked `(on screen)`; to another it shows that session's tree. In a session that started none, and
on the home screen, it hides, and shows again in the next session with a tree. Closed with `q` or by
OpenCode, it stays closed.

**Stopping from the TUI.** `s` in the panel, or `/courier stop <session>` in the prompt (`/courier
stop` alone lists the open session's tree to pick from), asks the person to confirm with the session's
title and how many sessions are under it, then stops it with the open session as the caller: the same
stop as `courier_stop`, and the target's parent, when its turn was interrupted, is told with the usual
notice unless it is the caller itself. A toast says how many sessions were stopped and interrupted and
how many scheduled messages were cancelled, or why the stop was refused. `/courier` with anything else
shows its usage.

**Forgetting from the TUI.** `x` in the panel, on a `gone` row (a session OpenCode no longer knows,
kept on the roster because it is isolated or has children of its own on it), asks the person to
confirm with the session's title and id and what happens, then forgets it as `courier_cleanup` called
from its own parent, never with `force`, once the open session is found above it. A toast says what it
did: `Forgot "<title>"`, with `and removed its worktree` or `; its worktree was already gone`, or
`Kept "<title>" and its worktree: <reason>`, or why it was refused. On a live row `x` forgets nothing
and says so. The server checks again: a session OpenCode still has, or one it cannot look up for another reason,
is refused.

**Attention.** A join group's reports released to a session call for attention, with a notification
when the terminal is not focused and the `done` sound; a child's report to its parent plays the
`subagent_done` sound, without a notification, unless the reporting session is a native child, whose
turn ending OpenCode already sounds. A report held with its group sounds once, with its group's
release. Each delivery is notified once per TUI.

**The RPC.** `courier`, registered by every instance at its location, through the same use cases as
`courier_tree`, `courier_children`, `courier_stop` and `courier_cleanup`. Its contract is `treeRpc`
from `opencode-courier/rpc`, for a client's `client.rpc(treeRpc)`. The TUI asks at the open session's
own location, else the TUI's, else the server's default one. Over HTTP:

```
POST /api/rpc/courier/summary?directory=<location> {"input":{"sessionID":"ses_…"}}
{"output":{"running":0,"waiting":1,"idle":1,"groups":[{"name":"pair","reported":1,"members":2}]}}
```

- `summary {sessionID}`: the status entry's counts, of every session under it, with `stalled` when one
  is, the session itself included. An input without a `sessionID` is refused as `rpc.invalid_input`.
- `tree {sessionID}`: the panel's rows. Each row: `sessionID`, `parentID`, `title`, `depth` (a child of
  the session asked is at 1), `state` (`running`, `waiting`, `idle`, `stalled` or `gone`), `stalled`
  (since when the oldest message that did not wake it waits), `outcome` of its last turn, `stopped`
  (true when `courier_stop` stopped it since its last prompt), `report` (`state`: `owed`, `reported` or
  `ended`, with the report's `status` once reported, and `progressed`), `group` (`name`, `standing`),
  `isolated`, `created`, `idle` (when its last turn ended, if it is not running), `cost` in US dollars,
  `context` (a fraction of the model's context window; absent when unknown), `tool` (its last tool
  call's `name` and `at`) and `waits` (`{type: "permission", action, resources}`, `{type: "question",
  question}` or `{type: "form", title}`, the requests first, then the forms); times in epoch
  milliseconds. `truncated` is how many older sessions the listing left out, and `stalled` since when a
  message waits in the session asked, when it is stalled.
- `stop {sessionID, by}`: `courier_stop` for `sessionID`, called from `by`, which must be above it;
  answers `{stopped: [{sessionID, title, outcome}], cancelled: <count>}`, deepest first, or fails with
  the declared error `refused` and `courier_stop`'s message.
- `cleanup {sessionID, by}`: `courier_cleanup` for `sessionID`, called from its own parent once `by` is
  found above it and OpenCode answers that it no longer has the session (one it still has, or a lookup
that fails otherwise, is refused), without `force`; answers
  `{outcome}`, one of `forgotten`, `removed` or `gone`, or `{outcome: "kept", reason}`, or fails with
  the declared error `refused`.

### The asks inbox

Every permission request, question and form waiting on the person anywhere in the open session's
courier tree, answered in the TUI's dialogs with no model in between. It is opened by the command
`courier.asks`: its key `<leader>k` (`ctrl+x k` by default), the slash command `/asks` (alias `/ask`),
the command palette ("Courier: what waits on you"), or a click on the footer's entry while it shows
`waiting on you`. With no session open it says so; with nothing waiting, "Nothing in this courier
tree waits on you." While a permission prompt or form is shown in the session, OpenCode renders it in
place of the prompt and the footer is hidden, so open the inbox with `ctrl+x k`.

**What it lists.** The tree is courier's own, read from the roster, from the top of the open session's
lineage down, so every session of a tree lists the same (those past retention left out). It lists the
tree's permission requests and questions as `courier_status` lists them (`pending`), and each
session's forms, leaving out the question tool's own forms, which are listed as their questions. It
also lists the top session's own permission requests, first: chiefly the prompt [`courier_answer`'s
`once`](#a-child-that-asks-for-permission) has OpenCode show there, which OpenCode shows only in the
top session's view. Such a prompt reads `Permission (top session): courier_answer once for "<action>
<resources>"`, and the child's request it is for says `the top's prompt asks`: allowing the prompt
passes `once` on to the child, so the child's request needs no answer of its own (answered directly,
it settles and the prompt, once allowed, passes nothing on). Any other request of the top's own reads
`Permission (top session): <action> <resources>`. One line per ask, the top's first, then in
the order the inbox first saw them, and in the tree's order among those seen together:

```
Waiting on you (3)
  Permission (top session): courier_answer once for "shell echo courier-asks"   Root                 top session
  Permission: shell echo courier-asks         Root › Fix the bug › Write tests   depth 2 · group pair · the top's prompt asks
  Question: Greeting: Which greeting?         Root › Fix the bug                 depth 1
```

Each session is named by its current title; one the terminal does not know keeps the title it was
spawned with. A question whose call was cut off says `cut off, answered by message`. Searching
filters the list. While the list is shown it follows the tree, on the events the footer's entry
follows: 250 ms after the first of a burst it reads the tree again and, when the asks changed, shows
the new list in its place, with an ask that arrived added and one answered or dismissed elsewhere
gone. It closes once nothing is left. Shown again, the list starts with an empty search, as
OpenCode's select is not given a query. While an ask is being answered the list follows nothing; an
ask settled elsewhere meanwhile is reported when its answer is sent.

**Answering.** Choosing an ask opens its dialog; `esc` goes back to the list.

- A permission request: `Allow once`, `Always allow` (only when the request has something to save,
  which it names), `Reject`, or `Reject with a reason…`. It goes through OpenCode's own reply; a
  rejection always carries a message, the person's reason or `courier_answer`'s default, so the
  child's call fails and it carries on. The session told about the request gets [one settled
  notice](#a-child-that-asks-for-permission).
- A form: each field in turn (those whose `when` fails on the answers so far are skipped; a hidden
  one's `default` is sent when it has one): a choice for one with options (and an answer of the
  person's own where the field allows it), a yes or no for a boolean, several choices for a
  multiselect, typed text or a number otherwise; an optional field can be skipped, and each starts on
  its `default`. A field is asked again, with a warning, until its answer fits its limits (`minimum`
  and `maximum`, `minLength`, `maxLength`, `pattern` and `format`, a required or `minItems`/`maxItems`
  multiselect), so OpenCode does not reject the reply and lose the other answers; a typed field's
  placeholder shows its limits. The answer goes through OpenCode's own form reply, and the session
  told about the form gets [its settled notice](#a-child-that-shows-a-form). A form answered or
  dismissed elsewhere meanwhile is not counted answered: a warning says it no longer waits. A form
  that opens a page (an `external` field) is left to its own session.
- A question: each of its questions in turn, one choice, several (toggled, then `Done`) where it
  allows them, or `Type your own answer…`. The answers are passed on as `courier_answer` does, and
  the top session hears it once, [as a question settled without it](#a-child-that-asks-a-question):
  its own open question call asking the same is withdrawn with `answered by the person (…)`, else, if
  it was told about the question, it gets the settled notice (`answered="elsewhere"`). Answers that
  do not fit the question come back as a message in the TUI, and nothing is passed on.

**Attention.** 250 ms after the first of a burst of permission requests and forms, the TUI reads the
open session's tree and looks at each ask it has not seen before. The sound is OpenCode's own: its TUI
plays `permission` for a request and `question` for a form, and notifies when the terminal is not
focused, for every child but a native one, for which the courier adds one notification when the
terminal is not focused, with the ask and where it comes from. The asks already waiting when the TUI
starts, or when a tree is first read, are not announced, except those of the sessions the events name.

**The RPC.** `courier-person`, registered by every instance next to `courier`; its contract is
`personRpc` from `opencode-courier/rpc`:

```
POST /api/rpc/courier-person/asks?directory=<location> {"input":{"sessionID":"ses_…"}}
{"output":{"top":"ses_…","sessions":[{"sessionID":"ses_…","title":"Fix the bug","parentID":"ses_…","depth":1}],
  "permissions":[{"sessionID":"ses_top","requestID":"per_…","action":"shell","resources":["echo hi"],"passesOn":{"sessionID":"ses_…","requestID":"per_…"}},
    {"sessionID":"ses_…","requestID":"per_…","action":"shell","resources":["echo hi"],"save":["echo *"]}],
  "questions":[{"sessionID":"ses_…","requestID":"question_…","questions":[…],"stopped":true}]}}
POST /api/rpc/courier-person/answer?directory=<location> {"input":{"sessionID":"ses_…","requestID":"question_…","answers":[["Hi"]]}}
{"output":{"answered":true,"by":"result"}}
```

`sessions` has `group` for a member of a join group. `permissions` starts with the top session's own
requests, whose `sessionID` is `top` (not in `sessions`), for a tree with at least one session below
the top; one that `courier_answer` asked has `passesOn`, read from the request's `metadata`. `answer`
gives `{"answered": false}` for a question that no longer waits, and `problem` with the reason when
the answers do not fit. Forms are not in `asks`: the TUI lists them itself (`GET /api/session/:id/form`).

### The memory view

The project's [tree records](#memory) in a dialog, for a person to read, keep and clear. It is opened by
`/courier memory` or the palette's "Courier: memory", from a session or the home screen, and lists the
records of the project of the open session's location, else the TUI's, else the server's default one,
the pinned first and then newest first by when each last moved, grouped under `Pinned` (shown only
while a record is pinned) and then by that day as OpenCode's Sessions dialog groups sessions, `Today`
first and then each local date, one row each:

```
Memory (3)
  Pinned
  Split the parser 2 parts: 2 done · 12 min · $0.70 · shown 7 times, opened once
  lesson (2026-09-02): "The lexer and the parser collided in one file; give them to one session."

  Today
  Add memory to courier (this session) 3 parts: 2 done, 1 partial · 42 min · $1.28
  lesson (2026-10-17): "The docs part was ten lines; next time do it yourself."

  Fri Oct 16 2026
  Fix the bug no parts · 42 min · not finished · shown once
                                                                            forget x  pin p
```

Every date and time the view shows is local, in the TUI's zone (`TZ`), where `courier_recall` dates
the same record in UTC. The row's title is the top session's title (clipped to 46 characters; its id
when it has none), `(this session)` for the open session's own tree; after it the parts counted by
status, how long the tree ran, the parts' costs summed when any is known, `not finished` when it
is not, and how often other trees' `courier_recall` calls listed it and opened it in full (`shown 7
times, opened once`, from the record's [`reads`](#what-lies-beside-a-record); nothing while none has);
under it, muted, the lesson, dated on the local day and `from depth <n>` when a
sub-orchestrator wrote it, clipped to 160 characters and cut in the middle to the dialog's width (a
line the host's select draws though the plugin API does not declare it:
[plugin-api-notes.md](maintainers/plugin-api-notes.md#tui-and-rpc-entrypoints)). The dialog is the
widest OpenCode has, 116 columns, or the terminal's width. Searching filters the rows, by their titles
first and by their day too.

- `enter` shows the record in full, in three groups: **Tree** (the top session, when it started and
  last moved, to the minute in local time with the zone's short name, `2026-10-17 12:12 GMT+2`, how
  long it ran, its split line or `not stated` (not its revisions), `Finished` or `Not finished` with the cost in all,
  `Recalled <n> times`, first by the top when, or by a part only, else `Not recalled`, `Shown <n>
  times, opened <m>` by other trees' `courier_recall` with when last, else `Never shown`, and `Pinned`
  since when, else `Not pinned`), **Parts**
  (one row per session, indented by depth: title, status, depth, `isolated`, `group <name>`,
  duration, cost, `ctx <n>%` and spawns refused; `No parts` with none) and **Lesson** (`lesson
  (<day>[, from depth <n>])` and its text, wrapped at 90 characters; `No lesson` without one).
  `enter` or `esc` there goes back to the list, and a second `esc` closes it.
- `p` pins the record under the row, or in a record the record shown, and unpins a pinned one (the
  footer reads `pin` or `unpin` there), with no confirm: a pin is reversible. A toast says what the
  server did: `Pinned "<title>": listed first, never swept`, `Unpinned "<title>": kept as the others
  are`, or that there was nothing to pin, when the record was forgotten meanwhile. The list, or the
  record, is then read again, the cursor on the record, which moves into or out of the `Pinned` group;
  in a record, the footer's `pin` reads `unpin`, and the **Tree** group's `Pinned` row says since
  when. A pinned record is listed first by `courier_recall` too, marked `pinned`, and the sweep never
  drops it ([retention](#memory)).
- `x` forgets. In the list, the record under the row; in a record, on a **Lesson** row only the
  lesson, and on any other row the record. Each after a confirm that names the record and says what
  goes and what stays, with `Forget` and `Keep`. A toast says what the server did: `Forgot the record
  of "<title>"`, `Forgot the lesson of "<title>"; its facts stay`, or that there was nothing to
  forget, when another TUI or the sweep got there first. The list, or the record, is then read again;
  once the project has no record left, a toast says so and the view closes. In the list the cursor is
  then on the record that followed the one forgotten, or the one before it when it was the last, or
  the nearest still listed; `Keep` leaves it on the record kept. The search is cleared by a forget or
  a keep, as OpenCode's select takes no starting query.
- `esc` closes the view from the list, and goes back to the list from a record. Every letter but `x`
  and `p` can be typed in the search, `q` among them: `x` and `p` are footer actions, whose keys
  OpenCode runs before the search field sees them, and a plugin's footer action takes only a literal
  key.

With `"memory": false` in the plugin's options at the location asked, the view says in a toast that
memory is off in this project and lists nothing; with no record, that the project has none yet. The
view notes nothing on any record, and counts no read; forgetting removes the record's storage key with
what lies beside it, or writes the record back without its lesson, and nothing else: the tree's next
turn end writes a fresh record, without the lesson. Pinning writes only the pin key [beside the
record](#what-lies-beside-a-record), and unpinning removes it; the record itself is not written.

**The RPC.** `courier-memory`, registered by every instance next to `courier` and `courier-person`;
its contract is `memoryRpc` from `opencode-courier/rpc`:

```
POST /api/rpc/courier-memory/records?directory=<location> {"input":{}}
{"output":{"memory":true,"projectID":"proj_…","records":[{"sessionID":"ses_…","startedAt":1760000000000,"movedAt":1760000900000,
  "title":"Add memory to courier","split":"split: 3 parts: core, e2e, docs","finished":true,"recalled":{"at":1760000001000,"calls":1},
  "lesson":{"text":"The docs part was ten lines; next time do it yourself.","at":1760000890000},
  "reads":{"shown":7,"read":1,"at":1760001000000},"pinned":{"at":1760000950000},"parts":[…]}]}}
POST /api/rpc/courier-memory/forget?directory=<location> {"input":{"sessionID":"ses_…","lesson":true}}
{"output":{"outcome":"lesson"}}
POST /api/rpc/courier-memory/pin?directory=<location> {"input":{"sessionID":"ses_…","pinned":true}}
{"output":{"outcome":"pinned"}}
```

- `records {}`: the records of the project of the location asked, the pinned first and then newest
  first, each as [the record](#memory) has it with its top session as `sessionID`, its `reads` and
  `pinned` merged in and without `revisions`; `memory` is false, and `records` empty, when the option
  is off at that location.
- `forget {sessionID, lesson?}`: removes the record of the tree under `sessionID` in that project, with
  its pin and reads, or with `lesson` true only its lesson; answers `{outcome}`, one of `record`,
  `lesson` or `none` (no such record, or no lesson to drop). It forgets with the memory option off too.
- `pin {sessionID, pinned}`: pins the record of the tree under `sessionID` in that project, or with
  `pinned` false unpins it; answers `{outcome}`, one of `pinned`, `unpinned` or `none` (no such
  record). Pinning a pinned record keeps when it was first pinned. `pinned` is explicit rather than a
  toggle, so two terminals cannot flip each other's pin. It pins with the memory option off too.

## Worktree cleanup

An isolated child works in a git worktree under OpenCode's data directory
(`…/opencode/worktree/<project>/<name>`, on a detached HEAD), and nothing removes it on its own. When
the parent has what it needs from the child, it calls `courier_cleanup { sessionID }`, which removes
the worktree and drops the child from `courier_children`. A child started without `isolate` has no
worktree: `courier_cleanup` only forgets it (outcome `forgotten`), dropping its roster entry and report
state, and, for a member of a join group that has not reported, [dropping it from the
group](#join-groups). `courier_cleanup` never deletes a session. Deleting one in OpenCode (the TUI,
the app or `DELETE /api/session/<id>`) drops its report state and groups, and the report state of the
sessions it started. Its roster entry is forgotten at once when the child is not isolated and has no
children of its own on the roster; an isolated child's entry stays, so `courier_cleanup` can still
remove its worktree, and so does that of a session whose own children are still on the roster, as
their lineage runs through it, both listed with the error until `courier_cleanup` or the 14 days are
up. With [`nativeChildren`](#native-child-sessions) on, a deletion also deletes the session's native
children, and theirs, forgotten the same way: each deletion forgets its own entry first if it is a
leaf, so the whole chain goes when the deletions arrive leaf first, and when the parent's arrives
first its entry stays until it expires.

### Nested isolation

A root session's isolated child starts from the project's last commit. When the session calling
`courier_spawn` with `isolate: true` is itself an isolated child on the roster, the new worktree
starts from the commit **the parent's worktree is on now**, so a sub-orchestrator hands its committed
work down; that commit is the child's recorded base. Uncommitted work is not handed down: the brief of
an isolated session tells it to commit before it spawns, and when the parent's worktree has
uncommitted changes `courier_spawn` says so in its result (the spawn goes on).

- A parent whose roster entry could not be indexed is taken for a root, and its children start from
  the project.
- If the parent's HEAD cannot be read (git missing, the worktree gone), `courier_spawn` fails and
  starts nothing; the error says to start it without `isolate`.
- Every isolated child is told to commit its work on a branch named `courier/<its session ID>` (it
  starts on a detached HEAD, so it creates it) and to name that branch in `artifacts.branch` of its
  report. The branch is in the shared repository, so the parent merges it into its own worktree.
  `courier_cleanup` counts the branch like any other: the commits on it are not "on no branch", and
  the commits a worktree was made from never count.
- How OpenCode makes a worktree from a commit: [plugin API
  notes](maintainers/plugin-api-notes.md#creating-a-worktree-from-a-given-commit).

The worktree is kept, and the result says why, when it holds work that would otherwise be lost:
uncommitted changes, untracked files included (ignored files, such as `node_modules`, are not work),
or commits that are on no branch, tag or remote-tracking ref, which is where a child's commits on its
detached HEAD end up. Commits on a branch survive the removal and do not count; nor do the commits
the worktree was made from, which `courier_spawn` records. The result lists up to 50 changed paths (an
untracked directory counts once) and 50 commits. Commit or branch what you want to keep (`git -C
<worktree> branch <name>` keeps its commits), or call `courier_cleanup` again with `force: true` to
discard it; `force` also removes a worktree git can no longer read. A worktree whose directory is
already gone is just dropped from the list; git forgets its registration on its next `git worktree
prune` or `git gc`.

The plugin runs git itself, looked for in its usual install locations and never through `PATH`:
`/usr/bin/git`, `/usr/local/bin/git`, `/opt/homebrew/bin/git` and `/run/current-system/sw/bin/git`
(NixOS and nix-darwin), or on Windows `C:\Program Files\Git\cmd\git.exe` and its `(x86)` twin. Git
installed anywhere else is named by the environment variable `OPENCODE_COURIER_GIT`, an absolute
path, set for the OpenCode server. Without a git, `courier_cleanup` refuses with a message naming the
places it looked, unless `force` is set, and `courier_spawn` records no commit.

Cleanup is explicit only: a child reporting back does not mean the parent has merged its work, and the
parent may still send it more to do in the same worktree. Isolated children whose worktree still
exists are kept on `courier_children` past the 14 days. `courier_cleanup` cannot tell whether the
child is still running, so call it after the child has reported. It works on the calling session's
own children.

## Scheduled messages

Pending `courier_later` messages are kept in the plugin's storage, and the plugin checks for due ones
every 15 seconds, so a message can arrive up to about 15 seconds late. Within one OpenCode server,
however many projects have the plugin loaded, one scheduler delivers, so each message arrives once.

They survive a server restart. After a start, OpenCode loads plugins for a project the first time that
project is used, so messages that fell due while it was down are delivered then. A crash between
delivering a message and forgetting it can deliver it twice after the restart.

## Two servers on one data directory

Two OpenCode servers on one data directory, such as `opencode serve` next to the background server of
`opencode service`, share the plugin's storage (the roster, pending `courier_later` messages, stored
questions) but not its memory. So:

- **A `courier_later` message, and a released [join group](#join-groups), is delivered by one server.**
  The servers agree through the storage on which one's scheduler delivers; when it stops gracefully,
  another takes over at its next tick, and after a crash or a stall within about 75 seconds, so the
  messages due meanwhile arrive late, not lost. The storage has no compare-and-set, so a message
  delivered twice is rare rather than impossible. A release of the plugin before 0.2.3 delivers on its
  own schedule beside it. The members' reports are held in the shared storage from whichever server
  runs them, and the delivering server sends the group at once when the last report is held, or the
  parent's turn ends, on that server, or at its next tick otherwise.
- **A child's permission request, its failed turn and its turn without a report are told to the parent
  once**, by the server that runs the child's turn. Whether a child owes a report compares the times
  of both servers' clocks, so they should be one machine's.
- **`courier_answer` passes an answer on only from a turn on that same server**, since pending
  requests live in the memory of the process running the child and the plugin API offers no channel
  between servers. From the other server it finds no request pending, asks the person nothing, and
  says so. `courier_status` likewise lists only the requests waiting on its own server.

Where you can, run one OpenCode server per data directory, or point a second one at another
(`XDG_DATA_HOME`).

## Webhooks

The receiver is off unless the plugin has a `webhook` option ([the README](../README.md#webhooks) has
the entry). Put it in the **global** config, since there is one receiver per OpenCode server. From a
local clone, `package` is the path to its `dist` directory. `"webhook": true` takes every default. If
the option is given more than once, the first location to load wins, and the others log that their
settings are ignored.

| Option | Default | |
|---|---|---|
| `port` | `4097` | Port to listen on. |
| `host` | `127.0.0.1` | Address to bind. Only this machine can reach the default. |
| `secretFile` | | File holding the shared secret (`~` is expanded). |
| `secretEnv` | `COURIER_WEBHOOK_SECRET` | Environment variable holding it, when there is no `secretFile`. |
| `maxBytes` | `1048576` | Largest body accepted. |

The secret is never read from `opencode.json` itself (a `secret` key is refused), so the config can be
committed. Make one with `openssl rand -hex 32 > ~/.config/opencode/courier-webhook-secret` and
`chmod 600` it. A file is the safer choice with `opencode service start`, whose environment may not be
your shell's. Without a usable secret the receiver does not start, and the server log says why.

On GitHub, add a webhook to the repository (Settings → Webhooks) with content type `application/json`,
the same secret, and the events you want (pull request reviews, review comments, issue comments, pull
requests, check suites or workflow runs). By default the receiver only listens on `127.0.0.1`: forward
a public URL to it with a tunnel you trust (`cloudflared tunnel --url http://127.0.0.1:4097`, `ngrok
http 4097`, or `smee --url https://smee.io/<channel> --target http://127.0.0.1:4097/github`, which
needs no inbound port) and use `<public URL>/github` as the payload URL. Only signed deliveries are
acted on.

The receiver starts when OpenCode loads the plugin, which after a server start happens the first time
a project is used. Until then deliveries fail; GitHub does not retry them on its own, but lists them
under Recent Deliveries with a Redeliver button.

Once it runs, `courier_subscribe` ties a session to a topic, and the plugin turns deliveries into
messages for the subscribed sessions, each queued behind any running turn and waking the session if
idle:

- `POST /github` takes GitHub webhook deliveries. A pull request review, a review comment, a comment, a
  pull request or issue being opened, reopened, closed (or merged) or marked ready for review, or a
  completed check run, check suite or workflow run on a pull request goes to the sessions subscribed
  to `owner/repo#N` and to `owner/repo`; anything else with a repository (a push, a release) goes to
  `owner/repo` only. Pings, CI runs that have not completed, and other pull request and issue actions
  (pushes to the branch, edits, labels, assignments, review requests) wake nobody.
- `POST /hook/<name>` takes anything else, for sessions subscribed to `<name>`. A JSON body's `text`,
  `summary` or `message` field is delivered, otherwise the body itself.

Every delivery must carry an `X-Hub-Signature-256` header: `sha256=` followed by exactly 64 hex
digits, the HMAC-SHA256 under the shared secret. For GitHub that is of the raw body. For
`/hook/<name>` it is of the name, a newline and the body, so a captured delivery cannot be sent to
another topic:

```bash
sig=$(printf '%s\n%s' deploys "$body" | openssl dgst -sha256 -hmac "$SECRET" -r | cut -d' ' -f1)
curl -X POST -H "x-hub-signature-256: sha256=$sig" --data-binary "$body" http://127.0.0.1:4097/hook/deploys
```

A missing or wrong signature gets `401`, and the body is not parsed. The check is constant-time.
Bodies over 1 MiB (`maxBytes`) get `413`. A delivered event gets `202`, with the number of sessions it
reached, which can be 0. The digests of the last 1000 accepted deliveries are remembered in memory,
and a delivery already accepted gets `200 already delivered`; one that reached nobody because every
delivery to a session failed is forgotten again, so it can be retried. So a GitHub Redeliver of a
delivery that already arrived is ignored, and redelivering one that failed works. Generic senders that
post the same text twice should add something unique, such as a timestamp, to the body.

The subscribed sessions are sent their messages at once, so a session slow to take one holds up none
of the others. A session that OpenCode no longer knows loses its subscriptions the next time a
delivery for it fails, and `courier_subscribe` refuses a session id that does not exist.

A session sees a short summary (event, repository and number, who, state or conclusion, link, and at
most 1500 characters of a review or comment body), wrapped in `<courier from="github" event="...">`
and followed by a note that it is outside text, to be treated as data. Review and comment bodies are
written by whoever can comment on the repository, so subscribe sessions only to repositories whose
commenters you trust with your agent's attention. The server log gets one line per delivery (event,
delivery id, number of sessions), never the payload or the secret.

GitHub does not report check suites on pull requests from forks, so CI results for those reach
`owner/repo` subscribers only. There is no GitHub event for a merge conflict.
