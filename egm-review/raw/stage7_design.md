# Stage 7, raw report of egm-design (Design Critic)

Target: egm-review/courier-orchestrate.SKILL.md, lines 1-51. Status: completed. Persona, context file and the feature-spec standard were read; the standard's core principle (a fresh session can follow it correctly and the procedure addresses its own failure modes) was applied, not its section template. Claims were checked against src/skill.ts, src/tree (spawn.ts, group.ts, limits.ts, text.ts, context.ts, tools.ts, cleanup.ts), src/person (events.ts, text.ts, tools.ts), src/scheduling, src/memory, docs/reference.md and docs/maintainers/plugin-api-notes.md.

No Blocker. Eight Majors, six Nits.

MAJOR 1. Lines 20, 23, 39. The parent's own checkout is assumed clean, and nothing says so. An isolated child's worktree starts from the project's last commit (reference.md 519); src/tree/spawn.ts parentWork (lines 119-129) only checks for uncommitted work when the parent is itself isolated, so a root with a dirty checkout (it "did a small part itself", or the person's tree was dirty) gets no warning: its children never see that work, and line 39's `git merge courier/<session>` fails outright when the uncommitted files overlap the branch ("local changes would be overwritten"). The skill never tells the parent to commit before spawning or before merging. Recommendation: add to line 20 "commit your own checkout first: isolated parts start from its last commit, and a merge into a dirty checkout fails".

MAJOR 2. Lines 48, 34. Replacing a failed sub-orchestrator duplicates work, and the counting claim is wrong. Trace: a child that split its part has its turn fail while its own children are running. The parent gets `failed="..."` and line 48 says "start a replacement". But the failed child's children keep running; their group release (group.ts release, delivery "steer") wakes the failed child, which resumes, so two sessions now do the same job. Also, src/tree/limits.ts lines 44-48 count every ancestor of a live session as live, so "a failed turn does not [count toward the limits]" (line 48) is false whenever the failed session has live descendants; a replacement spawn can then be refused for a reason the skill said could not apply. Recommendation: in line 48, before "or start a replacement", add "after courier_stop on it if it has sessions of its own (one courier_tree shows), since those would wake it"; and qualify the counting sentence with "unless sessions under it are live".

MAJOR 3. Lines 27, 49, 50. Nothing bounds the wait, and the only safety net is optional and under-specified. (a) The check-in is "for long work" only, yet it is the sole cover for a failure the plugin cannot see (reference.md 360-361: server down) and for an unsealed group: per plugin-api-notes.md 160-166 a plain Reject of the prompt that `courier_answer once` opens ends the top's step with no `time.idle`, and group.ts `sealed` reads `time.idle`, so a group whose members have all reported is not released until the top ends another turn; nothing wakes it but a check-in or the person. (b) The skill says nothing about what to write in the check-in or what to do when it fires: a session woken by one with reports still out has no rule (the courier_children description allows "a one-off look, e.g. on a scheduled check-in"; the skill forbids courier_children outright in line 27). (c) A check-in that fires after all reports arrived and was not cancelled is not described; a model may re-verify or re-spawn. (d) courier_cancel needs the id (scheduling/tools.ts); there is no listing tool, so after a compaction the id is gone and the check-in cannot be cancelled. (e) With two groups in flight (group.ts byGroup supports several per parent; line 20 and 23 both produce them) "cancel it when the reports arrive" is ambiguous. Recommendation: make it one check-in per group, worded "if every report of group X is in, do nothing; else one courier_children, then message, drop or stop the member that is out", keep its id in your reply, and cancel it on the group's release.

MAJOR 4. Lines 27, 29, 35. Permission and question notices reach the top only, and the skill tells every session otherwise. src/person/events.ts reportAsked sends to `topOf(chain)` and person/question/answer.ts to `asked.top`; reference.md 402-404 says so. So for a sub-orchestrator, "a question, a permission request ... each start a new turn for you" (line 27) and "propose once with courier_answer" (line 29) never happen, and "your own permission prompts are relayed nowhere" (line 35) is false: a sub-orchestrator's own prompts are relayed to the top like any child's. The stall claim in line 35 holds either way. Recommendation: prefix line 29 with "At the top:" and change line 35 to "The root's own prompts are relayed nowhere".

MAJOR 5. Line 34. The partial rule has no exit. Trace "a child reports partial twice": the group releases with the partial (group.ts holds partial; a later one replaces it); the parent sends "finish it"; the child reports partial again, delivered on its own; line 34 again says "have the session finish it". Nothing caps the rounds, so a child that cannot finish produces a tree that never ends, each round costing a turn. Recommendation: "have the session finish it once; if it is partial again, do the rest yourself or carry the gap in your own status".

MAJOR 6. Line 22. `native: true` for a part that "checks" is unsafe off the TUI. A checking part runs a shell, so it asks permission; a native child's prompt shows only in the view of its nearest non-native ancestor (courier_spawn's `native` description; reference.md 660 "Use native children only with OpenCode's TUI or the paired app"), and under `opencode run` without `--auto` or a bare API client it is rejected or seen by no one (reference.md 666-668, 676-678). The top is told `shown="native"` and line 29 then has it call nothing. The skill gives the host caveat nowhere. Recommendation: in line 22 add "and only when the person works in the TUI or app, where its prompts show".

MAJOR 7. Line 21. "Say whether it may split its part further" is a lever the plugin does not provide. src/tree/text.ts splitRule puts the split rule in every brief below maxDepth unconditionally, and the role line repeats it; the task text can only ask. Trace "a child told it may split spawns a group of its own": its report waits on its group, the parent's group waits on it, and a silent grandchild blocks both; the silent-end notice goes to the child alone, so the parent sees only a group that does not close (back to Major 3). The parent also cannot budget maxTotal, since line 14 has every job repeat the shape. Recommendation: either state the limit honestly ("its brief lets it split by the same rule; say so only to forbid it, when depth or total is short") or have the maintainers make the brief honour the task's say.

MAJOR 8. Lines 7, 13, 15. A root that is itself an OpenCode subagent is not addressed. src/tree/context.ts gives depth null (root) to any session without roster lineage that has courier_spawn among its tools; nothing hides the courier tools from a session OpenCode's own subagent tool started inside a tree (reference.md 686-708 lists such subagents in the tree but not in the roster). Such a session reads line 13 and 15 as its own: it calls courier_recall, may "start exactly one session for the whole task", and starts a second tree with its own record, its own maxTotal budget and permission relays to a session nobody opens. Recommendation: add to line 7 "if OpenCode's subagent tool started you, do not split: report to the session that started you".

NIT 1. Lines 20, 39. "No two parts edit the same files" cannot hold for lockfiles and generated files (this project's own test/__snapshots__/notices.test.ts.snap is one), and "resolve conflicts yourself" invites hand-merging them; "run the checks once more" is the only catch. Recommendation: "regenerate lockfiles and generated files rather than merging them by hand".

NIT 2. Lines 20, 23. The isolation rule covers editors only. A non-isolated part that reads files another part edits runs in the parent's checkout, sees the pre-change state, and sees it change if the parent merges a branch while it runs. Recommendation: add to line 23 "or reads what another edits".

NIT 3. Line 50. After a compaction the skill text itself may be gone, and the role line points to the skill only "before you split". The standing entry survives (reference.md 207-217), but the plan, group names, check-in ids and which branches were merged do not. Recommendation: in line 16's reply line, also list the group name and check-in id, so a summary keeps them.

NIT 4. Lines 39, 51. courier_cleanup never deletes the `courier/<session>` branch (cleanup.ts inspects branches, removes worktrees only), so every tree leaves one branch per isolated part; and line 51's "cleanup: true removes their worktrees" omits that one with uncommitted work or commits on no branch is kept (courier_stop's description). Recommendation: "removes their worktrees, except one holding work on no branch; delete merged courier/ branches yourself".

NIT 5. Line 44. The skill restricts the lesson to the top, but courier_note's description and reference.md 637-638 let a sub-orchestrator write one, and a second note replaces the first (noteText). A sub-orchestrator following the tool and a top following the skill silently overwrite each other. Recommendation: one clause: "a sub-orchestrator puts its lesson in its report, not in a note".

NIT 6. Lines 39, 43. "done ... verified and delivered" (line 43) and "merge nothing of it into your checkout" (line 39) mean two delivered whole jobs are never checked together by anyone; the parent's "run the checks once more" covers merged parts only. The playbook may own this, but the skill's `done` then asserts more than was verified. Recommendation: in line 43, "or verified and delivered (each on its own)".

Claims checked and found backed: group hold/replace semantics (line 20, 27), the isolated brief's merge instruction (line 21), skill permission per load (line 21), the split lines (line 16), courier_note's refusal over the limit (line 44), the `shown="native"` rule (line 29), the person's-word rule (line 30), courier_tree's `owes` field (line 50), courier_stop's subtree semantics (line 51), and the refusal names maxDepth/maxChildren/maxTotal (line 49).
