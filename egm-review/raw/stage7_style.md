# Stage 7, raw report of egm-style

Target: egm-review/courier-orchestrate.SKILL.md, lines 1-51. Status: completed. Read in full: the target, the persona, the goldfish context, src/skill.ts, test/__snapshots__/notices.test.ts.snap (all 1664 lines), src/tree/text.ts, src/tree/context.ts, src/kernel/protocol.ts, src/person/text.ts, src/memory/text.ts, docs/reference.md, CLAUDE.md, line_map.tsv. No style standard was supplied; the persona's audit vectors apply. Every redundancy claim below was checked against the snapshot (tool descriptions, briefs, role lines, notices).

Verdict: no Blocker. The procedure is sound in substance; the defects are three factual overstatements that need calibration, a large share of text that restates what the reader already has in a tool description, brief, role line or notice (and so costs tokens on every request for nothing), and several sentences whose structure hides the condition from the action. Every rewrite offered is shorter than the text it replaces.

MAJOR

1. Line 3 (description). The trigger is later than the skill's own first step. The description says "Load before you split a task", but step 1 (line 13) tells the root to call courier_recall and decide, and the root role line (snapshot line 701) says to load the skill before deciding. A model following the description loads it only after it has decided to split and skips step 1. The colon after "courier_spawn" also reads two ways (explaining "split", or starting a "load when" condition). The third sentence is a verbless topic list, acceptable for a description, but it omits the last section (a failed, silent or refused part). CALIBRATE. Rewrite (shorter): "How opencode-courier's session tools work. Load before you decide whether to split a task with courier_spawn: 2 or more independent, substantial parts touching separate files or areas. Starting the parts, waiting without polling, relaying questions and permissions, reading reports, merging, reporting upward."

2. Line 7, first sentence. "Your brief, or the opencode-courier role line in your system prompt, names your depth in the session tree and its limits." False for the reader this sentence most concerns: the root before its first spawn. Its role line (src/tree/text.ts lines 75-82, snapshot line 701) names neither depth nor any limit; only the depth-0 line written after the first spawn does. The brief and the sub-orchestrator role line do name them. CALIBRATE: "Below the root, your brief names your depth and the tree's limits." The second sentence (no courier_spawn means do it yourself) repeats the leaf role line and the leaf brief (snapshot lines 645, 699), and a leaf is not the description's reader. DROP.

3. Line 35, third sentence. "Your own permission prompts are relayed nowhere, and each one stalls the whole tree, as each request below you waits on the person". docs/reference.md lines 401-404: a request from any depth is relayed to the top session. So a sub-orchestrator's own prompts are relayed, and this sentence is true only of the root. The causal chain ("stalls the whole tree, as each request below you waits on the person") is also a reason longer than the rule it supports, and "a tool's own path" names nothing a model can act on. CALIBRATE and shorten: "Verify first-hand: open the files and run the checks yourself, through the project's scripts, so that one permission rule covers them; each prompt of yours waits on the person." ("Never hand the checking to another session" is already in the brief, snapshot line 628, and the root role line, line 693.)

4. Line 22, last clause. "leave it off for a part the person may want to open, or that should outlive you." The native parameter has three states (snapshot line 127): true, false, and unset, where unset lets the plugin's nativeChildren option decide. With that option on, "leave it off" read as "unset" makes the part a subagent, the opposite of the stated intent. The skill elsewhere says "unset" for model and variant (same line). CALIBRATE: "native: false for a part the person may want to open, or that should outlive you."

5. Line 15. Four problems in one bullet. (a) "as your brief says" is false for the root, which has no brief, and for a child it is the sentence admitting its own redundancy. (b) The list of what counts as a stage differs from the brief's and the reference's: the brief (snapshot line 626) and docs/reference.md line 177 add "the fixing of what a review found once you have verified it"; the skill omits it, so a child holds two definitions. (c) "Every other session never starts exactly one session for the whole task: it only adds a hop, and a chain of single hops uses up the tree's depth" is a negative restating the brief's "Never start exactly one session for the whole task", followed by a reason longer than the rule. (d) "its own context is worth keeping; it still verifies" shifts "it" between the task and the root. Action: keep the root exception (new information) and the stage list aligned with the brief; DROP the reason clauses. Suggested: "Only the root, the session nobody started, may start one session for the whole task, when the task is heavy (long reading, many edits, long runs) and the root's context is worth keeping; the root still verifies and integrates that report. One session for one stage is a part, not the whole: a core 2 or more parts follow, a review of the merged parts, or the fixing of what a review found once verified."

6. Line 16. The split-line templates and the prose share one punctuation set. The first form itself contains a semicolon ("split: no, because …; considered: <…>"), then " or " joins the second form, then "; the root has a third form" is prose. A fresh reader cannot tell template semicolons from sentence semicolons. Also duplicated verbatim in the brief (line 627) and root role line (line 701), so only the marking needs fixing. Rewrite (shorter): "Say which in one line of your reply before you start: `split: no, because …; considered: <the parts you weighed>` or `split: <n> parts: … (one phrase per part)`; at the root also `split: 1 part: <the task>, to keep my context`."

7. Line 21. One bullet of seven instructions, several with a trailing reason longer than the rule. "how to check it so that one permission rule covers the checks (step 4)": the parenthesis reads as a reference or as an instruction. "it sees the same list, not your choice" is cryptic. "one permission rule for skill covers their loads, as one covers the checks" asserts something about OpenCode's permission matching that no listed file supports (docs/reference.md line 227 says only that loading asks the skill permission); DROP the clause, the instruction stands without it. "Say whether it may split its part further, and when the part is a whole job that delivers itself (step 5), since an isolated session's brief otherwise says its branch is for you to merge": "when" reads as temporal or conditional, "delivers itself" is undefined (see finding 9), and the "since" clause is longer than the rule. Suggested middle and end: "Name the skills it should load, from those listed to you (it sees the same list). Say whether it may split further, and whether it delivers its own result (step 5) instead of leaving its branch for you to merge."

8. Line 23. The parallelism breaks: "starts once that one is done: merged into your checkout, or, when it was delivered (step 5), started with isolate: true and told to merge" makes "started" and "told" look like states of the finished part. Rewrite (shorter): "A part that depends on another starts after you merge that one's branch. If that one was delivered instead (step 5), start the dependent with isolate: true and tell it to merge courier/<session> of the delivering session first."

9. Lines 21, 23, 39, 43: "delivers itself", "delivered", "delivers it and reports where", "verified and delivered". "Deliver" is never defined (a PR? a deploy? a file written outside the repo?), and line 39's "reports where" dangles. One definition at line 39 would carry the other three uses: "When a part is a whole job whose result goes somewhere other than your checkout (a deliverable), its session puts it there and reports the place; verify it there and merge nothing of it." That is not longer than the current sentence and removes "still naming its courier/<session> branch when it is isolated", which the brief already requires of the child and which line 23 covers for the parent.

10. Line 27. Of three sentences, two restate text every reader has at the moment of action. "do not poll with courier_children, courier_tree or sleep" is in the brief (line 628), in courier_spawn's description (line 76, in capitals) and in every spawn result (lines 822-834). The courier_later sentence is the last sentence of courier_spawn's description and the whole of courier_later's (line 486). The list of what wakes you is the one new thing, and it omits a form, which docs/reference.md line 321 lists. DROP the duplicates: "Reply without calling more tools. The group's reports, a blocked report, a message without a status, a question, a permission request, a form, a failed turn or a silent end each start a new turn for you."

11. Line 29. After "follow the notice", every sentence restates a notice: "propose once ... or reject with the reason when the person has told you to refuse it or it plainly goes against what they asked" is snapshot line 1120 almost word for word; "the person decides in OpenCode's prompt" is line 1116; "ask the person with your question tool, with the questions the notice gives" is line 1319; "When the notice says OpenCode already shows it ... call nothing unless they give you their answer" is lines 1187-1189 and 1380-1382; "Never answer for them" is in all of them. "their answer goes on by itself" is also only true when the question tool is used with the notice's exact wording (docs/reference.md lines 448-451; the unlinked case has its own notice, line 1402), so as written it overclaims. DROP to: "Answering from below: follow the notice, and never answer for the person."

12. Line 30. "Passing a message on: when it changes ..." never says what message. The reference (lines 252-253) names the sources: a child's finding sent without a status, a message from the person, one from your parent. A reader meets "it" five times before any noun. Add the subject in place of nothing: "Passing on a message from below, from the person or from your parent: when it changes ...". "Progress goes to no one" reads as a fact about delivery as easily as an instruction; the brief's "Progress alone is not worth a message" (line 620) is the model. Nit within this finding: "those parts" after "only to the sessions it affects" switches noun (see naming, finding 17).

13. Line 44. Everything after the first clause is courier_note's description (snapshot line 595): the list of what a lesson is, "Name the job it comes from and the reason", the limit and the refusal-not-clipping, and the AGENTS.md rule; the over-limit refusal (line 1641) also says "write it shorter" when it happens. In addition, "At the top" contradicts the tool, which allows "the top session or one that started sessions, never a leaf" (line 595; docs/reference.md line 637), so a sub-orchestrator reading the skill will not write a lesson the tool wants. CALIBRATE the scope and DROP the rest: "At the top, or as a sub-orchestrator that verified its parts, before you report: one courier_note if the next tree in this project should know something about running one like this; none when there is nothing."

14. Lines 48-51 ("When a part goes wrong"). Each bullet restates the notice or tool description the reader will have in hand at that moment: line 48's actions are the failure notice (line 974) and the silent-end notice (line 1023) verbatim, and "A silent end counts toward the limits until it reports" is line 1024; line 49's actions are the refusal texts (lines 755-761); line 50 is courier_tree's description ("For a one-off look, not for waiting", line 329) plus courier_children's ("e.g. after a compaction or restart", line 306), and the standing entry (line 1646) already keeps the parent current without any call; line 51 is courier_stop's description (line 352), including "Use it when a subtree went wrong or is no longer needed", and the skill drops that description's caveat that worktrees holding unbranched work are kept (CALIBRATE if kept). The only new facts are "a failed turn does not [count], until you message it again" (supported by docs/reference.md lines 365-366) and "do not retry in a loop". Keep those two: "A failed turn (failed="...") or a silent end (ended="without-report"): do as the notice says. A silent end counts toward the limits until it reports; a failed turn does not, until you message it again." and "A refusal from courier_spawn: do as it says; retry when a report has arrived, not in a loop." DROP lines 50 and 51, or reduce 51 to "A subtree to abandon: courier_stop its first session, with cleanup: true for its worktrees."

15. Line 13. "first call courier_recall once, before you decide and never in a loop" says the same thing four ways, and the tool description (line 572) already says "Call it once at the start, not in a loop"; the root role line (line 701) says "call courier_recall once". The second sentence ("Below the root, read none: the records describe whole trees, which the root weighed before it split") is the tool description's second clause verbatim, and "read none" is an odd verb for "do not call it". Rewrite: "At the root, call courier_recall once before you decide. Below the root, do not call it."

16. Line 9. "is a playbook's" is jargon with a dangling possessive, and "a skill for that" has no clear antecedent (the planning? the reviewing? the playbook?). Rewrite: "This skill says how the tools behave. Planning the parts, staging a core and reviewing the merge are not in it: if a skill for them is listed to you, load it too."

17. Naming, whole document. (a) "root" (lines 13, 15, 16) versus "top" (line 44 "At the top", line 51 "its top session" meaning the first session of a subtree): three uses of "top", two senses, where line 15 has already defined "root" as "the session nobody started". Pick "root" for the tree and "first session" for a subtree. (b) "part" is both a unit of the task (line 14) and the session doing it: "native: true for a part" (22), "courier_stop those parts" (30), "When a part goes wrong" then "message the session" (46-48). Say "session" wherever a tool is applied. (c) "failed" is a report status (line 34: "failed: read the error") and a turn outcome (line 48: failed="..."). Line 34's "read the error" sounds like the turn case; say "failed: read what went wrong" to match the brief's definition (line 617). (d) "your checkout" (lines 23, 39) versus the tools' "worktree" and "directory"; a non-isolated parent has no worktree of its own, so "checkout" is defensible, but it is a third word for the same place; one would do. (e) "leave it off" versus "unset" (finding 4).
