FINDINGS

1. Major. Lines 21, 23, 39 ("a whole job that delivers itself", "when it was delivered (step 5)", "a whole job with a deliverable of its own, its session delivers it and reports where").
The skill offers two integration modes, merge or delivered, and the orchestrator must pick one per part at step 2, in the task text, before any report exists. The criterion for "delivers itself" is never stated, nor what "deliver" means in tool terms (push a branch? open a PR? write to a path outside the checkout?). Line 14 says "4 tickets are that many parts" but not whether a ticket is merged or delivered. Nothing resolves it at run time: the isolate parameter description and the brief both say "merge that branch yourself", so the tools only know the merge mode. Reader (a) with three independent parts in one repository has to guess whether these are "whole jobs" and, if so, what to tell each session to do with its result. Guidance: give the criterion in one clause on line 21 (for example: "a part delivers itself only when its result lives outside your checkout: a PR, a release, another repository") and move the definition up from line 39 to where it is first used, or drop the delivered mode from the skill and leave it to the person's task text.

2. Major. Line 22 ("native: true for a part that only reads ... leave it off for a part the person may want to open, or that should outlive you").
"Leave it off" is ambiguous between unset and false, and the two differ: the courier_spawn schema says "false starts a standalone session, whatever the plugin's nativeChildren option says; unset, that option decides". With nativeChildren on, "leaving it off" (unset) produces exactly the subagent the sentence wants to avoid, one that is deleted with the parent. The tool description resolves the semantics but not the skill's intent, so the session must guess which the author meant. Guidance: write "native: false" in place of "leave it off".

3. Major. Line 27 ("For long work, courier_later a check-in for yourself, and courier_cancel it when the reports arrive").
Three values the step needs are unnamed: what counts as long, the delay (delayMinutes or at is required by the schema, and neither is suggested), and what the check-in message should say or trigger. The courier_children description ("For a one-off look, e.g. on a scheduled check-in") resolves what to do when it arrives; nothing resolves the delay or the threshold, so readers (a) and (b) each pick a number. For reader (c), after a compaction the later-id is gone from context and no tool lists scheduled messages, so "courier_cancel it" cannot be executed; the consequence is only a stray wake-up, but the instruction is unexecutable as written in that state. Guidance: name a default ("about twice the time you expect the longest part to take") and say what the message should tell you to do ("look once with courier_children").

4. Major. Line 50 (reader c: "Lost track, after a compaction or a restart: one courier_tree shows every session under you ... whether it still owes a report").
courier_tree, courier_children and the standing instruction entry (text.ts standingEntry) all show the children's side: reported done, owes a report, ended without one, group standing. None shows the orchestrator's side: whether it already verified, merged and cleaned up the two reports that are in. With two reports in and one outstanding, the root after compaction must guess whether to merge courier/<a> and courier/<b> again, and whether it already re-sent the outstanding one (line 48) once. The information exists in git (git branch --merged, worktrees still present after courier_cleanup) but the skill does not point there, and no tool or notice does either. Guidance: add to line 50 one clause: "git branch --merged and the worktrees still present show which reported branches you have already merged and cleaned up".

5. Nit. Line 44 versus the courier_note description.
The skill allows a note only "At the top, before you reply to the person"; the tool accepts one "From the top session or one that started sessions, never a leaf", and the recall listing shows "lesson (..., from depth 1)". Reader (b), a depth-1 sub-orchestrator that learned something, must guess whether to note it or put it in its report; the noteLeafRefusal says "put what you learned in your report instead" only for leaves. The skill's choice (top only) is a decision made, so not a gap, but it silently narrows what the tool permits. Guidance: either say "a session below the top puts it in its report" or drop "At the top".

6. Nit. Line 21 ("how to check it so that one permission rule covers the checks (step 4)", "one permission rule for skill covers their loads").
"Permission rule" is OpenCode configuration vocabulary (reference.md line 231 shows action "skill"); a fresh session knows what command to write into a task, not which rule the person has. Line 35 explains the intent for the orchestrator's own checks ("through the project's scripts rather than a tool's own path") but line 21 is where the task text is written and that explanation comes two steps later. Guidance: on line 21 say "name one project script for all its checks" and leave the permission reasoning to line 35.

7. Nit. Lines 21 and 23 use "delivered (step 5)" and "step 4" before those steps define the terms, and line 23 cannot be acted on before step 5 is read. Readable because the whole skill is loaded at once, but it is the one place a step relies on a later one. Resolved by finding 1 if the definition moves up.

8. Nit. Line 20 (isolated worktrees from the root).
The isolate description warns about uncommitted changes only "From a session that is itself isolated"; spawn.ts applies the same HEAD-only start to any parent, and the spawnText warning ("Your worktree has uncommitted changes, which it does not see") arrives only after the spawn. Reader (a) with a dirty root checkout learns too late. Guidance: in line 20, after "isolate: true", add "commit first: its worktree starts from your HEAD".

9. Nit. Lines 16 and 27 ("Say which in one line of your reply, before you start" and "Reply without calling more tools").
A fresh session may read "reply" as ending the turn and wonder whether the split line must go out in a turn before the spawns. The brief uses the same words, so the model is at least consistent; the split line can be text emitted before the tool calls in one turn. Guidance: "in one line of your reply, in the same turn as the spawns".

10. Nit, outside the target but bearing on reader (c). The depth-0 role line (rolePart 1 in text.ts, "root orchestrator") does not tell the session to load the skill, unlike rolePart 2/3 for sub-orchestrators and rolePart 5 for a fresh root. If a compaction drops the skill text, the root has only tool descriptions for steps 4-6. Nothing in the skill can fix that; noting it for the maintainers.
